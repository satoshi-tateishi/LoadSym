# LoadSym パイロット版 仕様書

本書はパイロット版の**確定仕様**を記録する。実装前の構想段階の内容を含む場合は「将来対応」と明記する。
実装が進んだ段階で、本書は「実装済みの内容のみを記録する」形式へ改訂する。

- 最終更新: 2026-08-17
- 参照実装: 社内アプリ **TFViewer**（GitHub Pages + Supabase + パスワード認証）の構成を踏襲する

---

## 1. アプリケーション概要

- **アプリ名**: `LoadSym`（ロードシム）
- **目的**: 舞台音響現場における限られたトラック荷台スペースへの機材効率的なパッキング（積み込み）を可視化・シミュレーションする Web アプリケーション。
- **ターゲット**: 舞台音響スタッフ（社内利用を想定）
- **単位系**: 長さはすべて **mm（整数）**、重量は **kg**。

## 2. システム構成・インフラ

- **フロントエンド / ホスティング**: GitHub Pages
    - 公開ルートは `main` ブランチの `docs/` ディレクトリ。push がそのまま配信される（ビルドは行われないため、ビルド生成物もコミットする）。
    - `docs/.nojekyll` を置き、Jekyll による処理を無効化する。
- **バックエンド / データベース**: Supabase
    - PostgreSQL、認証（Auth）、行レベルセキュリティ（RLS）を利用する。
    - Supabase 無料プランの自動停止を防ぐため、GitHub Actions で日次の keepalive リクエストを送る。
- **フロントエンド技術**:
    - 素の ES Modules（アプリコードはバンドルしない）、MPA（1 HTML = 1 画面）、ページ遷移は `window.location.href`。
    - Alpine.js（UI 状態）、htmx（共通ヘッダーと機材フォームのHTMLパーシャル読み込み）。外部 CDN は**バージョン固定＋SRI＋crossorigin**。
    - Tailwind CSS v3（`npm run build:css` で生成、生成物をコミット）。
    - `@supabase/supabase-js` は esbuild で単一 ESM ファイルにバンドルし、`docs/assets/vendor/` に自己ホストする（ESM の import に SRI を付けられず CDN 依存を避けられないため）。
    - 荷台図の描画は **SVG**（Canvas ではない）。機材1個 = 1 `<g>` として DOM イベントを利用でき、機材名テキストがそのまま印刷・PNG 出力に乗るため。

## 3. 認証・ユーザー管理

- **認証方式**: パスワードログイン（Supabase Auth）
- **アカウント運用**: 管理者が Supabase ダッシュボードで事前にアカウントを作成・配付する。アプリ側にサインアップ導線は設けない。ユーザー自身によるプロファイル変更も不可。
    - **アプリからアカウントを新規作成・削除することはできない**（10章）。管理画面で行えるのはロール変更と有効/無効の切り替えまで。削除の代わりに `disabled` フラグを使う。
- **セッション**: supabase-js の既定（localStorage）に任せ、独自のトークン管理は行わない。
- **ログインエラー**: アカウントの存在を推測されないよう、常に汎用文言に丸める。
- **アカウント無効化**: `profiles.disabled` を立てると、次回アクセス時に強制ログアウトし `index.html?reason=disabled` へ遷移する。同時に DB 層でも全書き込みが不可になる（8章）。

### 3.1 ロールと権限

ロールは **Admin / Editor / Viewer** の3種類。`profiles.role` で管理する。

| 操作 | Admin | Editor | Viewer |
|---|:--:|:--:|:--:|
| 共通テンプレート機材・車両の閲覧 | ○ | ○ | ○ |
| 共通テンプレート機材・車両の作成/編集/削除 | ○ | × | × |
| **自分の**機材・車両の作成/編集/削除 | ○ | ○ | × |
| **自分の**機材・車両を共通テンプレートへ引き上げ／引き下げ | ○ | × | × |
| **他ユーザーの**機材・車両の閲覧 | ○ | ○ | ○ |
| **他ユーザーの**機材・車両の編集/削除 | × | × | × |
| **自分の**レイアウトの作成/保存/削除 | ○ | ○ | × |
| **他ユーザーの**レイアウトの閲覧 | ○ | ○ | ○ |
| **他ユーザーの**レイアウトの編集 | × | × | × |
| 他ユーザーのレイアウトを自分用に複製 | ○ | ○ | × |
| シミュレーター上での機材の配置操作 | ○ | ○ | ×（読み取り専用） |
| ユーザー管理（ロール変更・無効化） | ○ | × | × |
| CSV インポート（テンプレート） | ○ | × | × |

補足:
- **Editor は自分が作成したデータのみ編集できる**。他ユーザーが作成したデータは閲覧のみ。
- **Viewer は完全に閲覧のみ**。シミュレーターは読み取り専用モードで開き、ドラッグ・回転・保存の操作を受け付けない。
- Admin は他人の作成データを編集できない（テンプレートの管理者であってユーザーデータの管理者ではない）。ただしユーザーの無効化は可能。
- 権限は**三重にガード**する: ①ナビゲーションでのリンク非表示/グレーアウト → ②ページ側のロール判定とリダイレクト → ③**最終的な担保は RLS**。

### 3.2 テストアカウント

リポジトリ直下の `test-account.json`（gitignore 済み、非公開）に Admin / Editor / Viewer の3アカウントを記載する。ロールごとの権限差分は、複数アカウントでログインして比較検証する。

## 4. 画面構成

| 画面 | ファイル | 概要 |
|---|---|---|
| ログイン | `docs/index.html` | パスワードログイン。GitHub Pages のトップ |
| シミュレーター | `docs/simulator.html` | メイン画面。左右2カラム |
| レイアウト一覧 | `docs/layouts.html` | 保存済みレイアウトの一覧 |

### 4.1 シミュレーター画面

ブラウザ画面を左右に分割した2カラム構成。

- **左側（シミュレーター表示部）**
    - 上段に選択したトラックの荷台を **2D 見おろし・床面積ベース**で、**横向き**に表示（6.1節）。
    - 機材のドラッグによる配置、90度回転、スナップ、干渉検知のエリア。
    - トラックは**最大3台まで同時表示**して比較・シミュレーションできる（横向きのため縦に積んで並べる）。
      **常に最低1台は保持する**（4.2節）。機材はトラック同士の間を**ドラッグでまたいで移動できる**。
    - 各トラックのリアゲート側（画面右側）に**仮置きゾーンを常設**する（4.2節）。
    - 荷台には 100mm 間隔のグリッドと、周囲に寸法目盛り（尺規）を表示する。
    - 集計パネルを常時表示する（6.5節）。
- **右側（データ・操作タブ）**
    - **機材シンボルタブ**: 機材リストを表示し、左側へドラッグして配置する。
    - **トラックタブ**: 車両リストを表示し、選択した車両を左側のスロット（1〜3）に読み込む。
    - 各リストは次の3セクションに分けて表示する。
        1. **共通テンプレート**（`user_id = null`）
        2. **自分のデータ**（編集可）
        3. **他のユーザーのデータ**（閲覧のみ・追加ボタンなし）

### 4.2 リアゲート側の仮置きゾーン

実際の積み込みは「その現場に必要な機材を先に荷台の後ろへ出しておき、そこから荷台へ積んでいく」
という手順で進む。画面上でも同じ流れをなぞれるよう、**各トラックのリアゲート側（画面上は荷台の右側、
奥行き方向の延長）に仮置きゾーンを常設**する。専用の置き場ブロックは持たず、各トラックの荷台図の
一部として描く。

- **位置とサイズ**: 実際の荷台の奥（画面右）に、全トラック共通の基準奥行き `REFERENCE_DEPTH_MM`
  （10,000mm。11tトラックの最大値 9,500mm に余裕を持たせた値）までを仮置きゾーンとする。
  実荷台ぶんは実線の白、仮置きゾーンは破線のグレーで区別し、ある程度の幅があれば
  「仮置き（未積載）」と表示する。11tトラックのように実寸が基準に近いトラックでは、
  仮置きゾーンはごく僅かになる。
- **各トラックが個別に持つ**: 複数台読み込んだ場合、仮置きゾーンもトラックの数だけ存在する
  （共有の置き場は無い）。
- **トラックが1台も無い状態では機材を配置できない**。新規レイアウトはトラック0台から始まり、
  右の「トラック」タブから最初の1台を読み込むまでは配置操作を受け付けない。
- **最後の1台のトラックは削除できない**（常にトラックを最低1台は保持する）。トラックを外す
  「削除」ボタンは、読み込み台数が2台以上のときだけ表示する。
- **配置ルールはトラックの荷台と同じ**: 移動・スナップ・空き探索・クランプは、実荷台の奥行きに
  かかわらず基準奥行き `REFERENCE_DEPTH_MM` までを対象にする。そのため実荷台をはみ出す配置も
  棄却されず（6.3節-5）、荷台に入りきらない機材の逃がし先も兼ねる。
- **実荷台をはみ出した機材は赤くなる**（6.3節-7）。「本当に積めているか」の判定は常に実荷台の
  寸法で行うため、仮置きゾーンにある機材はエラー表示の対象になる。ただしクリアランス判定
  そのものは実荷台内の配置と同じ基準を使う（重なりだけでなく隙間不足も見る）。
- **自動配置（6.2節）は実荷台の範囲だけを詰め直す**。仮置きゾーンにある機材も、実荷台に
  収まるならそちらへ詰め直される。
- **高さ・積載重量の制限はない**（データ上は `null` = 制限なし）。
- **集計**: 積載率ではなく「**積み込み待ち N 点 / 合計 X kg**」を表示し、空になると「積み込み待ちなし」と出す。
  これにより「まだ積んでいない機材」が一目で分かる。
- **移動手段はドラッグのみ**。ドラッグ中はドロップ先のエリアが強調表示される。
  どのエリアでもない場所で離した場合は、掴む前の位置に戻る。
- **エリアをまたぐドラッグでは、移動先に着地点のプレビュー（破線のゴースト）を出す**。
  ドラッグ中の機材は掴んだエリアの中でしか動けない（ポインタキャプチャの維持と、壁で止める必要のため）ので、
  プレビューが無いと落とすまで着地点が分からない。移動元の機材は薄く表示して「出ていく側」と示す。
- レイアウトと一緒に**保存・復元**される（積み残しの状態も記録される）。

### 4.3 レイアウト一覧画面

保存済みレイアウトを**2つの表に分けて**表示する。

1. **自分のレイアウト** — 開く / 名前変更 / 削除 が可能
2. **他のユーザーのレイアウト** — 開く（読み取り専用） / 自分用に複製 が可能

各行に レイアウト名、作成者、使用トラック、更新日時 を表示する。**2つの表で列構成を揃える**（自分の表では作成者が常に自分になるが、列がずれていると2つの表を見比べるときに視線が泳ぐ）。
**レイアウトを開く操作はレイアウト名のクリックに一本化**し、行末には名前変更 / 削除 / 複製して編集だけを置く。
機材の点数は一覧には出さない（図を開けば分かる情報で、一覧では絞り込みにも使わないため）。

### 4.4 機材フォームと形状エディタ

**カテゴリを選ぶと、識別カラーがそのカテゴリの既定色（§5.4 の `default_color`）に切り替わる。**
手で選んだ色があっても上書きする。現場ではカテゴリごとに色を揃えて使うのが前提で、
「カテゴリを変えたのに色が前のまま」のほうが事故になりやすいため。別の色にしたいときは、
切り替わった直後にパレットで選び直す。新規追加でフォームを開いた時点でも既定カテゴリの色が入る。

**ポップアップは13インチのノート（1440×900、ブラウザの表示領域で約790px）でスクロールせずに収める。**
入力欄とパレットを左右2カラムに並べ、パレットの1マスは18px固定にする。`aspect-square` だと
ダイアログ幅に比例して1マスが大きくなり、17行で1000px近くまで伸びてしまうため。
`max-h-[95vh] overflow-y-auto` は、それより小さい画面のための保険として残す。
「形を編集」を開いた状態だけは例外でスクロールする（描画キャンバスを狭めないことを優先）。

シミュレーターと管理画面の機材フォームには、機材の平面形状を作る**共通の形状エディタ**を置く。
同じ `docs/assets/js/shape-editor.js` を共有するのは、保存される形や入力検証が画面ごとにずれないようにするため。

- 既定は従来どおり幅 × 奥行きの矩形とし、「形を編集」を押した場合だけエディタを開く。
- SVG キャンバス上で矩形・円・凸多角形のパーツを追加し、選択・移動・削除・数値編集できる。円は矩形と同じ
  ドラッグ操作、多角形は頂点クリックで作る。選択した矩形は四隅の「角落とし」で8頂点以下の凸多角形へ変換できる。
- 多角形は凸形状だけを許可する。凹みは従来どおり矩形パーツを組み合わせて作り、種類の異なるパーツを含めて
  パーツどうしの重なりは禁止する（面積の二重計上を防ぐため）。
- **プレビューは既定で x（横＝奥行き）2000mm × y（縦＝幅）1000mm** を映す。キャンバスの縦横比が
  2:1 なので、この比なら枠いっぱいに描ける。右下の ＋／− で 500〜20000mm の段を切り替えられる。
  **形がはみ出す拡大はできない**（＋が無効になる）。全体が常に見えていれば、視点移動の仕組みが要らず、
  画面の外にある頂点を掴めないという事故も起きないため。
  ズーム段はユーザーが選んだ値を保持し、形が収まらなくなったときだけ自動で広げる。
- ハンドル・頂点番号・線幅は viewBox の幅からの比で描き、どの倍率でも画面上の大きさを揃える。
  グリッドの見た目の刻みも段に応じて 100 / 500 / 1000mm と変える（**吸着は常に 100mm、Shift で 10mm**）。
- **多角形の頂点は作図後に増減できる。** 選択中の多角形は各辺の中点に ＋ が出て、押すとそこに頂点が入る。
  中点は両隣と一直線に並ぶが、`isConvex` は共線を読み飛ばすのでそのまま保存できる。
  削除は頂点一覧の × で、3点までしか減らせない（それ未満は保存できないため）。
- **選択中のパーツは90度単位で回せる。** 軸はそのパーツの外形中心なので、回してもその場に留まる。
  向きは `geometry.js` の `toParts()` と同じにし、荷台上で機材を回したときと食い違わないようにする。
  回転で他のパーツと重なっても操作は止めない（重なりの検査は「形を反映」でまとめて行う）。
- 通常は 100mm グリッドに吸着し、Shift キーを押している間は 10mm 単位に切り替える。現場でよく使う
  丸い寸法を素早く作りつつ、微調整もできるようにするため。
- 編集中は外形寸法をプレビューし、「形を反映」すると外形 bbox を幅・奥行きへ書き戻す。
- 「矩形に戻す」で `shape = null` の通常矩形に戻せる。
- **エディタの座標入力は、CADと同じく画面の横軸を `x`・縦軸を `y` と呼ぶ**。プレビューは §6.1 の
  ビュー座標（横 = 奥行き、縦 = 幅、下が `幅 0`）で描くため、この呼び方だと入力した `x` が画面の横へ、
  `y` が縦へ動いて一致する。保存形式（`x` = 幅 / `y` = 奥行き）は §6.1 のとおり変えず、
  読み替えは `shape-editor.js` の列定義（`RECT_COLUMNS` / `CIRCLE_COLUMNS` / `POINT_COLUMNS`）に閉じ込める。
  `幅` / `奥行き` / `半径` は軸ではなく寸法の名前なので、呼び方は変えない。
- 多角形パーツを選択すると、プレビューの各頂点に入力欄と同じ番号を表示し、入力欄にフォーカスしている間は
  その頂点を黒く塗る。頂点が増えると、どの行が図のどの点かを対応づけられないため。
- 角落としの4つの入力欄は、プレビューの見た目どおり**左下 / 左上 / 右上 / 右下**の順に並ぶ。
- 機材リストには形状を示すバッジを出さない。荷台上のシンボルが実際の形で描かれるうえ、
  機材フォームを開けば「パーツ形状（外形 … mm）／通常の矩形」の表示で判別できるため。

## 5. データ仕様と制限

テンプレート（全ユーザー共通）とカスタムデータ（各ユーザーが作成）を同一テーブルに同居させ、`user_id` で区別する。

- `user_id = null` … 共通テンプレート
- `user_id = <ユーザーID>` … そのユーザーが作成したデータ

**Admin は登録済みの機材・車両を、この2つの間で行き来させられる。** 機材／トラックフォームの
「共通テンプレートとして登録する」を編集時にも切り替えられるようにしてあり、保存時に `user_id` を
`null`（テンプレートへ引き上げ）または自分のID（テンプレートから引き下げ）へ書き換える。
まず自分用に作ってから全員へ配りたい、という運用が実際にあるため。

チェックを触らなかったときは `user_id` を送らない。毎回送ると、他人のデータを開いたときに
所有者を奪ってしまうため。RLSは更新前の行と更新後の行を別々のポリシーで判定するので、
`*_update_own` → `*_update_template` の移動は既存ポリシーのまま通る（追加のポリシーは不要）。

**Editor / Viewer には、このチェックボックスを DOM ごと出さない**（`x-show` ではなく `x-if`）。
`x-show` は要素が残るため、開発者ツールから触れてしまう。あわせてクライアント側でも、
Admin以外からは `user_id` を一切送らない（`ownerIdForCreate()` / `withOwnerChange()`）。

最終的な担保はRLSで、追加の変更なしに以下がすべて拒否されることを実機で確認済み。

| 操作 | Editor | Viewer |
|---|---|---|
| `user_id = null` で直接INSERT | 拒否 (42501) | 拒否 (42501) |
| 自分のデータを `user_id = null` へUPDATE | 拒否 (42501) | 拒否 (42501) |
| 既存テンプレートのUPDATE | 0件更新（USINGで対象外） | 0件更新 |

### 5.1 機材データ (`equipments`)

| 項目 | 型 | 備考 |
|---|---|---|
| 名称 | text | 必須 |
| カテゴリ | uuid | `equipment_categories` への参照（必須）。5.4節 |
| 幅 / 奥行き / 高さ | int (mm) | 必須、正の値 |
| 重量 | numeric (kg) | 既定値 0 |
| 識別カラー | text | `#rrggbb`。UI では 255 色のパレットから選ぶ（5.5節） |
| 備考 | text | 任意 |
| 平面形状 | jsonb | `shape`。null は従来どおり幅 × 奥行きの矩形1枚 |
| stackable / 最大積載重量 | boolean / numeric | **将来の 2.5D 用**。パイロットでは未使用 |
| 並び順 | int | 管理画面から並び替えできる。シミュレーターの機材リストもこの順に並ぶ |

- `shape` は外形 bbox の左前を原点とするパーツの集合として持つ。保存形式は矩形
  `{ kind: 'rect', x, y, w, d }`、円 `{ kind: 'circle', cx, cy, r }`、凸多角形
  `{ kind: 'polygon', points: [{x, y}, ...] }`。判定時の正規化で全パーツに外接 bbox の
  `x / y / w / d` を導出し、吸着・押し出し・空き探索の既存設計を共通利用する。
- `width_mm` / `depth_mm` は形を持つ場合も**外形 bbox**として残す。一覧表示・CSV・並び替えと、
  空き探索の初期サイズに従来の列をそのまま使えるため。形状エディタが形の保存時に外形寸法を書き戻す。
- `shape` は jsonb なので、3種類の `kind` に対するDBマイグレーションは不要。
- パーツどうしは種類を問わず重ねられない。重なりを許すと配置率で同じ床面積を二重に数えてしまうため。
- **制限: 1ユーザーあたり最大 100 個**。DB トリガで担保する。テンプレート（`user_id = null`）は制限対象外。

### 5.2 トラックデータ (`trucks`)

| 項目 | 型 | 備考 |
|---|---|---|
| 名称 | text | 必須 |
| 荷台内寸 幅 / 奥行き / 高さ | int (mm) | 必須 |
| 最大積載重量 | numeric (kg) | 任意（null = 制限なし） |
| 備考 | text | 任意 |

- **制限: 1ユーザーあたり最大 5 台**。DB トリガで担保する。

### 5.3 荷台内の障害物 (`truck_obstacles`)

タイヤハウス、柱など**荷台内の配置不可エリア**を矩形で定義する。1台のトラックに複数登録できる。

| 項目 | 型 | 備考 |
|---|---|---|
| ラベル | text | 例:「タイヤハウス（左）」 |
| x / y / 幅 / 奥行き | int (mm) | 荷台左前を原点とする位置とサイズ（`x_mm` = 幅方向 / `y_mm` = 奥行き方向、§6.1 のデータ座標系） |
| 高さ | int (mm) | 任意（null = 床から天井まで） |

障害物は**不動**として扱い、機材の押し出し先にはできない。障害物と重なった機材はエラー表示（赤）になる。

トラックフォームの入力欄は、形状エディタ（§4.4）と同じく**画面の横軸を `x`・縦軸を `y`** と呼ぶ。
荷台図の目盛りと同じ読み方になるので、`x` 欄は保存列 `y_mm`（奥行き方向）に、`y` 欄は `x_mm`（幅方向）に
結び付ける。保存列の意味は変えない。

### 5.4 機材カテゴリ (`equipment_categories`)

機材の分類。**Admin のみが管理**し、全ユーザーが参照する。自由入力の text にすると
「SP」「スピーカー」のような表記ゆれで絞り込みが効かなくなるため、マスタに切り出している。

| 項目 | 型 | 備考 |
|---|---|---|
| カテゴリ名 | text | 必須・一意 |
| 並び順 | int | 小さいほど上。シミュレーターの絞り込みもこの順 |
| 既定の識別カラー | text | `default_color`。機材でこのカテゴリを選んだときに入る色。形式チェックは `equipments.color` と同じ |

初期カテゴリ: ミキシングコンソール / スピーカー / パワーアンプ / ラック / ケース / スタンド / その他

**既定の識別カラー**は、機材フォームでカテゴリを選んだ時点で識別カラーへ入る（§4.4）。
運用ではもともとカテゴリごとに色を揃えて使っており、1件ずつ255色から選び直すのは手間なため。
色は管理画面のカテゴリ編集から変更でき、コードには焼き付けない（現場ごとに好みが違うため）。
既定色を変えても**既存の機材の色は変わらない**。以後の初期値としてだけ効く。

使用中のカテゴリは削除できない（`on delete restrict`）。先に対象の機材を別のカテゴリへ移す必要がある。

**並び替えの操作**は2通り用意する（機材カテゴリとテンプレート機材で共通の仕組み）。

- **ドラッグ**（SortableJS）: 行の左端のハンドルをドラッグする。
  ただし **iOS Safari はドラッグハンドルへの touchstart を配信しない**ため、
  `(min-width: 768px) and (hover: hover) and (pointer: fine)` を満たす
  PC / Mac 相当の入力デバイスでのみ有効にする（画面幅だけで判定すると横向き iPad のような
  広いタッチ端末を含んでしまうため、hover / pointer も合わせて見る）。
- **↑↓ボタン**: 常に使える。タッチ環境ではこちらが唯一の手段になる。

どちらの操作でも、確定時に表示順どおりに `sort_order` を 10 刻みで採番し直す
（後から手で間に差し込めるようにするため）。値が変わらない行は更新しない。
ドロップ後は `oldIndex` / `newIndex` ではなく **DOM の実際の並び（`data-id`）を正**として確定させる。

テンプレート機材の並び替えは、対象の行だけを読み書きするため**ユーザー個人の機材には影響しない**
（シミュレーターの右ペインは「共通テンプレート / 自分のデータ / 他のユーザーのデータ」に分けて
描画しているため、並びが混ざることもない）。

### 5.5 識別カラーのパレット

機材の識別カラーは **255色（色相17段階 × 明度15段階）のパレット**から選ぶ。
`docs/assets/js/palette.js` に定義があり、機材フォームでは色見本のグリッドとして表示する。

- **赤系（色相 345〜20度）は含まない**。はみ出し・障害物との干渉が起きた機材を赤 `#ef4444` で
  塗りつぶすため、識別色に赤を使うと「エラーなのか元の色なのか」が区別できなくなる。
- 機材は不透明度 70% で白地に重ねて描かれ、その上に黒い機材名が乗る。淡すぎると枠が見えず、
  濃すぎると文字が読めないため、中間の段階（shade 5〜10 あたり）が最も読みやすい。
- 管理画面の CSV インポートタブから、**パレット255色を CSV で書き出せる**（Excel 用に BOM 付き UTF-8）。
  スプレッドシートで機材リストを作るとき、`color` 列に貼る値をここから選ぶ。
  列は `id, color, group, shade, r, g, b`。R/G/B はスプレッドシート側で条件付き書式に使える。
- CSV インポートでは任意の `#rrggbb` を受け付けるが、赤系が指定された場合は**警告を出す**
  （取り込み自体は続行する）。

### 5.6 レイアウト（積み込み計画）

シミュレーション結果は**名前を付けて複数件保存**できる。

- `layouts` — レイアウト本体（名前、備考、作成者）
- `layout_trucks` — レイアウトに読み込んだトラック（スロット 1〜3）
- `placements` — 各トラックに配置した機材（座標、回転角）。実荷台をはみ出した座標も、
  リアゲート側の仮置きゾーン（4.2節）にある配置としてそのまま保存する。

`slot` 列は過去の仕様（機材置き場をスロット0として保存していた頃）の名残で `0〜3` を許可する
CHECK 制約のままにしてあるが、現行の保存処理がスロット0の行を作ることはない。それより前に
保存されたレイアウトにスロット0の行が残っている場合、読み込み時にその行は無視する
（トラック本体の配置には影響しない）。

`layout_trucks` と `placements` は、参照元のトラック・機材が削除・変更されても保存時の図が壊れないよう、**寸法・名称・色をスナップショット（jsonb）として保持する**。

- **制限: 1ユーザーあたり最大 300 件**。DB トリガで担保する。
  容量のためではなく、保存の繰り返しで際限なく増えることへの歯止め（実測でレイアウト1件は満載でも 6〜8KB、1配置あたり約 300B）。
  レイアウトは成果物そのものなので、機材・トラックの制限と違って**実運用では到達しない値**にしてある。

## 6. コア機能・シミュレーション仕様（UI / UX）

### 6.1 座標系と表示の向き

**データ上の座標系**は、荷台の左前（進行方向前方・左）を原点 `(0,0)`、`x` を幅方向、`y` を奥行き方向とする。すべて整数 mm。

**画面表示は横向き（landscape）**にする。荷台は幅より奥行きが長いため（2tロングなら 1700 × 4400mm）、実寸の向きのまま描くと縦長になって画面の左右を持て余すため。

- 画面の**左が進行方向の前方**（運転席側）。図の左下に「◀ 前方（運転席側）」と表示する。
- 画面の**下が荷台の左側**（`x = 0`）。
- 変換は描画時のみ行い、データ側の座標系は変えない。`geometry.js` / `packing.js` は影響を受けず、
  SVG の `transform` で回転させた場合のように文字が寝てしまうこともない。

```
ビューX = 荷台の y（奥行き）
ビューY = 荷台の w − 荷台の x（幅）
```

**リアゲート側の仮置きゾーンも同じ座標系**を使う（4.2節）。実荷台の奥（`y` が大きい側）へ座標系を
そのまま延長しているだけなので、エリアをまたいでドラッグしても機材の向きは変わらない。

SVG の `viewBox` は実寸 mm で取り、CSS 幅でスケールする（ズーム＝`viewBox` の操作）。奥行きは
どのトラックも仮置きゾーンを含めて共通の基準奥行き `REFERENCE_DEPTH_MM` を使うため、
カラム幅いっぱい（CSS `width:100%`）で描くだけで**全トラック共通の mm/px スケール**になる。
トラックによってスケールが変わると、同じ機材でも荷台間で大きさが違って見えて紛らわしいため。

機材1個の形は、全パーツを1枚の `path` にまとめて塗る。矩形だけなら従来の union 境界を外周線に使い、
円・多角形を含む場合はSVGマスクで線の内側半分と接合部を消して外周だけを残す。パーツごとに半透明で
塗ると重なった箇所だけ色が濃くなり、内側の境界線が残ると1個の機材に見えないため。
ポインターの当たり判定もこの形に沿うので、L字の凹みをクリックした場合は L字ではなく、
その凹みに置かれている別の機材を選択できる。

実装上、SVG と Alpine.js の組み合わせには次の注意がある。

- `<svg>` 内では Alpine の `<template x-for>` を使わない。SVG 名前空間の要素として生成されると
  `.content` を持たないため、マークアップを文字列で組み立てて `x-html` に渡す。
- `:viewBox="..."` のような属性バインドは使わない。HTML パーサが属性名を小文字化する一方、SVG の属性名は
  大小文字を区別するため、JavaScript から `setAttribute('viewBox', ...)` で設定する。

### 6.2 配置とスナップ

自由配置ではなく、「**トラック壁面**」および「**すでに配置済みのオブジェクトの縁**」に対して、
**クリアランス**を保った状態で吸着（スナップ）する。

**クリアランスはレイアウトごとの設定**とする。既定 10mm、設定できる範囲は 1〜20mm。どこまで隙間を確保するかは
現場によって変わる（詰めて積みたい日も、養生や積み下ろしの都合で余裕を取りたい日もある）ため、ユーザーに委ねる。
値は `layouts.clearance_mm` に保存する。全体設定にすると、5mm で組んだ図を 10mm 設定の人が開いたときに
配置の意図が変わってしまうため。

設定を変えても**既に置いてある機材は動かさない**。クリアランスは吸着先を決める値であって、確定済みの座標を
動かすものではない。次の操作から新しい値で吸着する。

**エラー判定にも同じ設定値を使う**（6.3節-7）。設定を広げると、その隙間を確保できていない機材がその場で赤くなる。
配置は動かさないので、どこを直せばよいかだけが伝わる。設定範囲の下限を 1mm にしているのは、0mm（機材どうしが
完全に接する）では手も吊りベルトも入らず、実際には積めない図になるため。

かつては「吸着の目標値」と「エラーの下限」を別々の数字で持っていたが、挙動を一言で説明できなくなるためやめた。
数字は設定値ひとつで、意味は「確保すべき隙間」に統一する。

なお**スナップが効き始める距離**（しきい値）はクリアランスとは別物で、画面上 12px 相当で固定する。ズームしても
操作感を保つため実寸ではなく画面px基準にしてある。ここをクリアランスに連動させてはいけない。
実測で 1px ≒ 11〜13mm なので、5mm は画面上 0.4px 相当となり、吸着がまず起きなくなる。

**Alt(Option)キーを押しながらドラッグして離すと、その操作に限りスナップを無効化する。** SX300のような多角形を、
斜面どうしが隣接するよう少しずらして置く場合、外接 bbox の辺へのスナップが意図したずらしを消すことがあるため。
無効になるのはスナップだけで、荷台内へのクランプ、形状どうしの重なり判定、クリアランス判定、連鎖押し出しは維持する。
同じ荷台内の移動と、仮置きゾーン・別トラックからの移動のどちらにも適用する。

スナップ候補は x 軸・y 軸を独立に評価する。

1. **壁面候補**: `x = c` / `x = W - w - c`（`c` = クリアランス。y も同様）
2. **隣接候補**: 既存機材の各パーツの左右・前後にクリアランスぶん空けて接する位置
3. **整列候補**: 既存機材と移動中の機材のパーツ辺を揃える位置（この候補のみクリアランスなし）

画面上おおよそ 10px 相当の実寸距離以内で最も近い候補に吸着する。候補がなければ 1mm 単位の素の座標を用いる。
候補は全パーツの**外接 bbox の辺**から作り、x 軸と y 軸を独立に評価する構造は変えない。円は外接矩形の
一番外側で吸着し、多角形の斜辺に沿う専用スナップは行わない。

**リストからクリックで追加するときの初期位置**（および複製時）は、荷台の空きを左前から探して置く。
探索の候補は「壁ぎわ」と「既存機材の各パーツの右／後ろにクリアランスぶん空けて接する位置」に限る。固定間隔の格子で
走査すると格子の目から外れた隙間を見落とし、実際に置ける場所があるのに「空きがない」と断ってしまう
（内寸 2363mm に幅 1160mm を2つ並べる位置 `x = 1180` は 50mm 刻みに乗らない）。
空きが見つからない場合は配置せず、その旨を通知する（6.3節-5 と同じ考え方）。

各トラックの「自動配置」は、そのトラック内にある全機材を、設定中のクリアランスを保って左前から詰め直す。
同一機材をコンパクトなブロックへまとめ、現状向きとグループ全体を90度回した向き、複数の幅比率を候補にする。
候補は既に置いた機材を含む部分配置の使用奥行きで選び、面積・奥行き・幅の3種類のグループ順による完成配置を比較する。
変更前と同じ向き・幅比率・面積順の戦略と、奥行き・幅の大きい個体から置く方式も、常に比較対象に残す
（変更前に到達できていた配置を探索から漏らさないため）。複合形状と障害物も通常配置と同じ判定を使う。
既存配置が正常で、再計算結果より使用奥行きが短い場合は既存配置を保持し、人手で作った理想型を悪化させない。

同一機材が5台以上ある構成では、1台を床面計算から外したときに使用奥行きが10%以上かつ250mm以上短くなる候補も比較する。
候補が成立した場合、その1台はデータから削除したり実際に重ねたりせず、床面配置の後方に単独で残したうえで、他機材への
縦積みを検討するよう通知する。これは高さ・耐荷重・積み先を決定しない提案に限り、`stack_level` は変更しない。
仮置きゾーンや他のトラックには影響しない。全点を正常に置けた場合だけ一括で確定し、1点でも置けない、または
最終検証で不正が残る場合は元の配置を一切変えない。成功した一括配置は履歴上の1操作とし、1回のUndoで元に戻せる。
Viewerおよび他ユーザーのレイアウトを読み取り専用で開いている間は実行できない。

### 6.3 回転と干渉処理

回転は **90度刻み**（0 / 90 / 180 / 270）とし、形自身の外形 bbox を基準に各パーツと多角形の頂点を回す。
吸着や押し出しを各軸の比較のまま扱えるため。機材を回転させた際に他のオブジェクトや
トラック壁面と干渉する場合は、次のように処理する。

機材どうし・機材と障害物の接触判定はパーツ対ごとの厳密形状で行う。矩形どうしは従来の軸判定、円は距離、
凸多角形はSATと辺間距離を使う。一方、**吸着・押し出し量・空き探索はパーツの外接 bbox 基準**を維持する。
動きの予測を安定させながら、L字の凹みや円・斜辺の外側を空きとして利用するため。

1. 回転させた機材を固定（pinned）とする。
2. 重なった相手を、pinned から離れる向きに最小移動量（＋クリアランス）で**スライド（押し出し）**する。
   複数のパーツ対が重なっている場合は、方向ごとに必要な押し出し量の**最大値**を採る。1組だけで量を決めると、
   その組を解消しても別のパーツが食い込んだまま残るため。
   押し出しを**始める**条件は押し手によって変える。pinned（ユーザーが動かした / 回転させたもの）は
   **クリアランス未満まで近づいていたら**押し、連鎖の先は**実際に重なったときだけ**押す。
   連鎖側までクリアランス基準にすると、クリアランス設定を広げたときに、既に詰めて置いてある対まで
   干渉とみなして荷台全体の再配置を始めてしまい、密な荷台では収束せず打ち切られる（結果が壊れるので
   棄却され、どの機材も動かせなくなる）。押し出す**距離**は連鎖の先でもクリアランスぶん取る。
3. 押し出された機材を新たな押し手として、幅優先で**連鎖的に**解決する。1サイクル内で各機材の押し出し方向は一度だけ確定させ、反復上限（100回）で打ち切る。
4. 障害物（5.3節）は不動として扱い、押し出し先にはできない。
5. 収束後に判定し、**リアゲート側の仮置きゾーンを含めた範囲（4.2節の `REFERENCE_DEPTH_MM` まで）
   にも収まらない操作は成立させない**。押し出した結果まで含めて全機材がこの範囲内に収まる場合だけ
   確定し、収まらなければ操作そのものを棄却して操作前の状態に戻す（回転なら向きも位置も元のまま）。
   実荷台に押し出す余地が無い場合は、仮置きゾーンへ逃がして解消する（その結果、押し出された機材は
   実荷台をはみ出すため6.3節-7の条件で赤くなる）。
   判定は「操作前に問題の無かった機材が、操作の結果はみ出す／重なる」かどうかで行う。単純に「結果が不正なら棄却」に
   すると、はみ出しを含む保存済みデータを開いたときに以後あらゆる操作が棄却されて直せなくなるため、
   **悪化させない操作は通す**。
6. 棄却したときは理由を通知する（例: 「回転させると荷台に収まらないため、回転できません。」）。
   押し出しが反復上限で打ち切られた場合も通知し、Undo で戻せることを案内する。
7. **エラー（赤色の塗りつぶし）の条件**は、荷台からのはみ出し、および壁・障害物・他の機材との隙間が
   **クリアランス設定を下回る**こと（接している状態を含む）。集計パネルには「要確認 N 点」として出す。
   通常の配置操作では上記の棄却により発生しないが、次の場合に現れる。
   - **クリアランス設定を広げたとき**。新しい隙間を確保できていない機材がその場で赤くなる。
     このとき配置は動かさない（勝手に動くと保存済みの図が変わってしまうため、動かす代わりに知らせる）。
     赤い状態でも編集はできる（棄却の判定は「操作前より悪化したか」の差分で行うため）。
     ただし棄却の判定は2系統に分ける。**荷台からのはみ出しと、設定範囲の下限 1mm を割り込む近さ**は
     物理的に不可能な状態として、設定値がいくつでも絶対に作らせない。クリアランス不足だけを差分で見る。
     ひとまとめにすると、設定を広げて全機材が赤くなった状態では、はみ出しや重なりを作る操作まで
     通ってしまう（どれも既に赤いので悪化を検知できない）。
   - 保存済みデータ由来のはみ出し。
   - **リアゲート側の仮置きゾーン（4.2節）にある機材**。実荷台の寸法で「収まっているか」を判定するため、
     仮置きゾーンにある間は常に赤くなる。ただし壁との隙間不足としては判定しない
     （仮置きゾーンの外壁は実荷台の壁ではなく `REFERENCE_DEPTH_MM` の位置にあるため）。重なり・クリアランス
     判定そのものは実荷台内の配置と同じ基準を使う。
   - 荷台の幅いっぱいに近く、両側にクリアランスを取る余地がない機材は、荷台に収まっていれば良しとする。
     そうしないと、動かしても直しようのない赤が残ってしまう（ドラッグ・ナッジの停止位置と揃えてある）。
   - 壁との判定は形状の各パーツではなく**外形 bbox**で行う。荷台幅いっぱいの機材に対する上記の逃がし方を、
     ドラッグ・ナッジで使う `clampToBed` と揃え、「直しようのない赤」を作らないため。
8. **移動時の壁**: ドラッグとナッジでは、機材は壁からクリアランスぶん内側で止まる。幅方向（左右）は
   実荷台の壁で止まるが、**奥行き方向（前後）は実荷台の壁では止まらず、リアゲート側の仮置きゾーンの
   外壁（`REFERENCE_DEPTH_MM`）で止まる**。荷台の幅いっぱいに近い機材ではその余地が無くなるので、
   そのときはクリアランスを諦めて範囲内に収める。
   **エリアをまたぐドラッグの着地点も同じ扱い**にする。端で離しても「収まらない」と弾かずに壁で止める
   （プレビューに見せた位置と実際に落ちる位置を一致させるため）。

### 6.4 高さの扱い（パイロット版）

パイロット版の配置計算は**完全に床面積ベース**で行い、高さは参照値として扱う。

- 機材の高さがトラック荷台内寸の高さを超える場合は警告表示する。
- **将来対応（2.5D）**: 機材の上に別の機材を積む「段積み」に対応する。すべての形は高さ方向に
  真っ直ぐ立ち上がる柱（直方体・多角柱・円柱）に限定する。立体の干渉判定を
  「2D形状の重なり × 高さ範囲の重なり」に分解し、現在の2D判定をそのまま使えるようにするため。
  高さの合算表示、スタックされた機材名のテキスト表示、トラック内寸高さに収まっているかの判定を行う。
  この拡張のため、`placements` に `stack_level` / `stack_parent_id`、`equipments` に `stackable` /
  最大積載重量のカラムを**最初から用意しておく**（パイロットでは `stack_level = 0` 固定）。

### 6.5 範囲・面積・重量の可視化（集計パネル）

以下をリアルタイムで表示する。

- 荷台床面積に対する**配置率**。矩形は幅×奥行、円は `πr²`、多角形は頂点の靴紐公式による実面積を合計し、
  外形 bbox の凹みや円の外側は除く。矩形だけのレイアウトでは従来の値から変わらない。
- **総重量** と **最大積載重量に対する比率**（超過時は警告表示）
- **要確認の機材の件数**（はみ出し、およびクリアランス不足の合計。6.3節-7）
- **荷台内寸高さを超える機材の件数**
- 選択中の機材の寸法、および壁までの残り寸法。
  **トラックブロックの直上**に置く（操作の対象と図を目線を動かさずに見比べられるため）。
  未選択でも枠は残して案内文を出す。選択のたびに出入りさせると、その都度トラックが上下にずれてしまう。
  **キーボード操作の説明は右端に固定**する。左詰めのままだと機材名や寸法の桁数で位置が動いてしまう。

### 6.6 操作補助

- **Undo / Redo**: `Ctrl+Z` / `Ctrl+Shift+Z`。連動押し出しで意図しない結果になった場合の救済手段（履歴は最大 50 件）。
- **キーボード操作**: 矢印キー = 10mm 移動（Shift 併用で 1mm）、`R` = 90度回転、`Delete` = 削除、`Ctrl+D` = 複製。
  荷台は横向きに描画するため、矢印キーの向きは**荷台座標ではなく画面上の見た目**に合わせる（`→`で画面右へ動く）。
- **グリッド / 尺規**: 荷台に 100mm 間隔のグリッド、周囲に寸法目盛りを表示。
- **メッセージの出し分け**: 性質で置き場所を変える。
  - **一時的な通知**（操作の結果。棄却の理由、クリアランス変更、保存完了など）は、
    **トラックブロックの下端に重ねて**表示し、5秒で自動的に消える。通常のフローに置くと表示・非表示のたびに
    下の荷台がずれて読みにくいため。荷台SVGは下端に 420mm 相当の余白（尺規とキャプションだけの帯）が
    あるので、重ねても図をほとんど隠さない。居座らせると図を覆うので必ず自動で消す。
  - **エラー**（保存失敗など）と**状態の説明**（他ユーザーのレイアウトを読み取り専用で開いた等）は
    消えては困るので、従来どおり通常のフローに置く。
  - いずれも印刷には出さない。
- **機材シンボルの表示**: シンボルに書くのは**機材名のみ**とする（寸法は選択時に集計パネルへ出るため、
  シンボルに重ねると枠からはみ出す）。枠が画面上で縦長になる向きのときは、名前を長辺に沿って寝かせて描く。

### 6.7 対応デバイス

**PC（マウス）を優先**し、タブレットでも操作できるようにする。ドラッグは HTML5 Drag and Drop を使わず、**Pointer Events で統一**してマウスとタッチを同一のコードパスで扱う。

## 7. 出力・共有

- **PNG 書き出し**: 現在の配置図を PNG でダウンロードする（SVG をシリアライズし、2倍解像度で canvas に描画して出力）。
  複製した SVG から Alpine のディレクティブ属性を除いてからシリアライズする。`:style` や `@pointerdown` は
  HTML 上では有効でも XML の属性名としては不正で、そのままでは画像として読み込めないため。
- **レイアウトの共有**: 保存したレイアウトは**ログインユーザー全員が閲覧できる**。編集できるのは作成者のみ。他ユーザーのレイアウトは「自分用に複製」して編集する。
- **印刷**: `@media print` で A4 横1枚に収まる専用レイアウトを提供する。ナビゲーションと右ペインを非表示にし、荷台図と機材リスト表を出力する。

## 8. データベース設計の基本方針（RLS 活用）

Supabase の行レベルセキュリティにより、データベース層で安全にアクセス制御を行う。クライアント側のガードは UX のためのものであり、権限の担保ではない。

### 8.1 アクセス制御の方針

| 操作 | 条件 |
|---|---|
| SELECT（全テーブル） | 有効なログインユーザーであること。**共通テンプレート・他ユーザーのデータも読み取れる** |
| INSERT / UPDATE / DELETE（自分のデータ） | ロールが Admin または Editor、かつ `user_id = auth.uid()` |
| INSERT / UPDATE / DELETE（テンプレート `user_id is null`） | ロールが Admin |

子テーブル（`truck_obstacles` / `layout_trucks` / `placements`）は、親テーブルの所有者を辿って判定する。

> 注: 当初案の「個別データは本人以外アクセス不可」は、**「他ユーザーのデータは読み取り可・書き込み不可」に変更**した。社内利用であり、他人の組み方を参考にできることの価値が、データを隠す必要性より大きいため。

### 8.2 ロール判定

RLS ポリシー内で `profiles` を直接参照すると再帰が起きるため、判定は security definer 関数 `current_user_role()` に集約する。この関数は `disabled = true` のとき `null` を返すため、**フラグ1つで全ユーザーの書き込みを一括停止できる**。

### 8.3 ユーザー一覧の取得

`auth.users` の email は PostgREST から参照できないため、Admin 画面のユーザー一覧は security definer の RPC `admin_list_users()` を用意する。関数内で呼び出し元が Admin であることを明示的にチェックする。

### 8.4 ユーザーの表示名

レイアウト一覧の「作成者」列と画面右上の名前には `profiles.display_name` を出す。
**新規ユーザー作成時に、メールアドレスのローカル部（@ より左）を既定値として保存する**（`handle_new_user()` トリガ）。
メールアドレスは1人1つで必ず異なるため、手入力なしで一意な表示名になる。

`display_name` はあとから書き換えられる列のままにし、**本人と Admin が読みやすい名前へ変更できる UI を別途用意する**（パイロット版の範囲外。それまでは Supabase ダッシュボードから変更する）。

作成者名は `profiles` を直接読ませず、表示名だけを返す RPC `layout_owner_names()` 経由で取得する（メールアドレス等の露出を避けるため）。

### 8.5 登録数制限

機材 100 個 / トラック 5 台 / レイアウト 300 件の制限は BEFORE INSERT トリガで担保する（機材・トラックは `user_id is not null` の場合のみカウント）。クライアント側のチェックだけに頼らない。
トリガは日本語のメッセージで `raise exception` する。`error-messages.js` は変換ルールが無ければ元のメッセージを返すため、そのまま画面に出る。

### 8.6 マイグレーション運用

Supabase CLI は使わず、`project-docs/sql/` に `NNN_snake_case_description.sql` の連番ファイルを置き、Supabase ダッシュボードの SQL Editor に貼って実行する。各ファイル先頭に「なぜこの変更をするか」を日本語コメントで記す。ロールバック用の down は作成しない。

## 9. テンプレートデータの整備

共通テンプレート（`user_id = null`）の機材・車両は、**Admin 専用の管理画面**から登録・編集・削除する。あわせて **CSV インポート機能**を提供し、機材リストを一括登録できるようにする。

- CSV は UTF-8（BOM 付きを含む）と Shift_JIS（Excel 由来）の両方を受け付ける。UTF-8 として厳格に
  デコードを試み、失敗した場合に Shift_JIS として読み直すことで判別する。
- 引用符で囲まれたフィールド（内部のカンマ・改行を含む）に対応する。
- 取り込みは「プレビュー → 確定」の2段階とし、行ごとに問題を明示する。
- **名称・幅・奥行き・高さが欠けている行のみを除外**し、残りは取り込む。カテゴリ名の不一致
  （「その他」に寄せる）や識別カラーの形式エラー（既定色を使う）は警告にとどめ、取り込みは続行する。
- 平面形状は CSV の取り込み対象にせず、CSV から作成した機材は `shape = null` の矩形とする。
  1行1機材の表形式に複数パーツを畳み込むと Excel から現場で書けるデータではなくなり、形はテキストで
  記述するより図を見ながら作るほうが速く正確なため。必要な形は取り込み後に機材を編集して付ける。
- ヘッダー行の列: `name` / `category` / `width_mm` / `depth_mm` / `height_mm` / `weight_kg` / `color` / `note`

### 9.1 管理画面のタブ構成

| タブ | 内容 |
|---|---|
| ユーザー | ロール変更・有効/無効の切り替え。自分自身の行は操作できない |
| カテゴリ | 機材カテゴリの追加・名前変更・並び替え・削除（5.4節） |
| テンプレート機材 | 共通テンプレート（`user_id = null`）の CRUD と**並び替え**。よく使う機材を上に集めておくと、シミュレーターの機材リストからも探しやすくなる |
| CSVインポート | 機材リストの一括登録 |
| バックアップ | 全テーブルのバックアップ作成（Dropbox保存）・復元（11章） |

ユーザー一覧の更新で RLS に弾かれた場合、PostgREST は権限不足でもエラーではなく 0 件更新を返す。
成功したように見えるのを避けるため、クライアント側で 0 件を明示的に失敗として扱う。

## 10. 却下した選択肢とその理由

| 選択肢 | 却下理由 |
|---|---|
| パイロット版から 2.5D（段積み）を実装 | 実装難度が大きく上がるため、まずは床面積ベースで実用性を検証する。ただしデータモデルには拡張余地を残す（6.4節） |
| 自由角度での回転 | 斜め配置の当たり判定（OBB/SAT）が必要になり実装コストが高い。トラック積載の実務では 90 度刻みで足りる |
| 回転時に押し出しを行わず赤色表示のみ | 仕様として連動押し出しが求められたため採用。誤操作の救済は Undo で担保する |
| Canvas による描画 | SVG のほうが DOM イベント・ヒットテスト・テキスト描画・印刷・PNG 化を素直に扱える。想定規模（3台×数十個）では性能上の問題がない |
| HTML5 Drag and Drop API | タッチデバイスでの挙動が不安定なため不採用。Pointer Events に統一する |
| レイアウトを非公開（本人のみ）とする | 社内ツールであり、他人の組み方を参考にできる価値のほうが大きい（8.1節） |
| 管理画面からアカウントを新規作成する | `auth.admin.createUser` は **`service_role` キー**を必要とする。LoadSym は静的サイトで JS がそのままブラウザへ配信され、しかもリポジトリが public なため、このキーを置くと RLS による保護が全て無効になる。実現するには service_role を Secret として持つ **Supabase Edge Function** が必要で、GitHub Pages 以外にデプロイ先が増える。社内利用でユーザー数が少なくアカウント作成の頻度も低いため、パイロット版ではダッシュボードでの作成を継続する。ユーザー削除も同じ理由でアプリからは行わず、`disabled` フラグで代替する |
| 誰でもサインアップできるようにして Admin が承認する | Edge Function は不要になるが、anon key は公開されているため第三者が無制限に `auth.users` の行を作れてしまう。「管理者が事前に作成・配付する」という運用方針とも合わない |
| バックアップ・復元を service_role キーや Supabase Edge Function で実装する | 9章と同じ理由（public リポジトリの静的サイトに service_role を置けない）。既存の `admin_list_users()` と同じ「security definer 関数 + 関数内で Admin 判定」のパターンだけで、追加インフラなしに実現できる（11章） |

## 11. バックアップ・復元（Admin専用）

Supabase 無料プランには自動バックアップの仕組みがなく、誤操作・CSV誤インポート等からの復旧手段がなかった。
管理画面（`docs/admin.html`）に「バックアップ」タブを追加し、**Admin のみ**が全テーブルのバックアップ作成・復元を行えるようにする。

- **バックアップ（読み取り）**: 対象8テーブル（`equipment_categories` / `equipments` / `trucks` /
  `truck_obstacles` / `layouts` / `layout_trucks` / `placements` / `profiles`）を1本の JSON に
  まとめる。Admin は既存 RLS（`profiles_select_admin` 含む）で全テーブルを読めるため、
  クライアント側の SELECT だけで完結し、service_role キーは不要。
- **保存先は Dropbox**（App フォルダのみにアクセスするアプリを利用）。認証は
  **PKCE OAuth**（App key のみで secret 不要）で、ブラウザだけで完結する。トークンは
  管理者本人のブラウザの `localStorage` に保存する（supabase-js のセッション管理と同じ方針）。
  Dropbox 未接続時・トークン失効時のために、作成直後のバックアップをローカルにダウンロードする
  導線と、ローカルの JSON ファイルから復元する導線も用意する。
- **復元（書き込み）**: RLS では他ユーザーの `user_id` 行を書けないため、`admin_list_users()`
  と同じ **security definer RPC** `admin_restore_backup(payload jsonb)`（`009_backup_restore.sql`）
  を使う。関数内で `current_user_role() = 'Admin'` を確認したうえで RLS をバイパスし、
  全テーブルを**丸ごと洗い替える**（部分復元は提供しない。運用がシンプルであることを優先した）。
  1回の関数呼び出しなのでアトミックに実行される（失敗時は自動的に全体がロールバックする）。
- **`profiles` は削除・挿入せず、既存ユーザー行の `role` / `display_name` / `disabled` を
  UPDATE するだけ**にする。`auth.users` は一切操作しない。アカウントの新規作成・削除は
  10章の既存方針どおりダッシュボード作業のままで、アプリから行うことはできない。
- **対象は同一 Supabase プロジェクト内での巻き戻し**（誤操作・破損からの復旧）に限定する。
  新規 Supabase プロジェクトへのフルディザスタリカバリは `auth.users` の UUID が
  変わってしまうため対象外（`equipments.user_id` 等の参照が壊れる）。
- 自動（cron）でのバックアップは行わず、**Admin がボタンを押した時の手動バックアップ**のみとする
  （利用者30人規模の社内ツールであり、運用をシンプルに保つことを優先した）。
