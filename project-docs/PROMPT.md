## 中 1: 障害物が「押し手」として働き、ユーザーが触っていない機材が黙って動く

**症状**: `docs/assets/js/packing.js:764` の `settle()` は `pinnedIds = [pinnedPlacementId, ...obstacles.map((shape) => shape.id)]`
として、障害物を「操作対象（pinned）」と同じ扱いで初期キューに入れている。`docs/assets/js/geometry.js:559` の
`resolveOverlaps()` は `const queue = [...pinnedIds];` でこのキューから押し出しを開始し、`geometry.js:587` の
`const trigger = pinned.has(pusher.id) ? clearanceMm : 0;` により、pinned な押し手（＝障害物を含む）は
**クリアランス未満まで近づいているだけで押し始める**。

その結果、障害物にクリアランス未満で接している別の機材（保存済みデータ由来の赤、または障害物追加後に赤くなった機材）が、
**その機材とは無関係な別の操作（遠く離れた機材のドラッグや回転など）のたびに、障害物からクリアランスぶん押し出されて座標が変わる**。
仕様6.3節-7は「クリアランス設定を広げたとき…このとき配置は動かさない（勝手に動くと保存済みの図が変わってしまうため）」と
明記しており、これに反する。

再現手順（`node`で再現スクリプトを書いて確認できる。荷台2400×5000、障害物(0,0,400×600)、機材A(400,10)を障害物に
クリアランス未満で接するよう配置、機材B(1000,3000)を用意し、`movePlacement(slot, 'B', {x:1000,y:3200}, 0, 10)` を呼ぶと、
Aに一切触れていないのに `A` の座標が `(400,10)` → `(410,10)` に変わる）。

**原因**: 障害物の「不動（押し出し先にできない）」という性質は `geometry.js:574` の `if (pinned.has(target.id)) continue;`
（＝押し出しの**対象**にはならない）で既に担保されている。障害物を初期キュー（＝押し出しの**起点**）に含める必要はなく、
これが不要な副作用を生んでいる。

**直し方の方針**:
- `packing.js:764` の `pinnedIds` は「押し出しの対象から除外する」用途と「押し出しの起点にする」用途の2つに
  使われているため、これを分離する。`resolveOverlaps()` 呼び出し側のシグネチャ（`geometry.js` の該当関数）に、
  「押し出し対象から除外するID集合」と「初期キューに入れるID集合」を別の引数として渡せるようにする
  （例: `resolveOverlaps(shapes, { excludeIds: pinnedIds, queueIds: [pinnedPlacementId] }, ...)`のように分ける、
  もしくは `queue` の初期値だけ `[pinnedPlacementId]` にし、`pinned`（除外用）は従来どおり障害物を含める）。
- `geometry.js:559` の `queue` は `pinnedPlacementId` 相当（ユーザーが実際に操作した機材）だけを起点にし、
  `pinned`（`574`行の除外判定に使う集合）は従来どおり障害物を含めたままにする。
- 他の呼び出し元（`resolveOverlaps` を使う箇所）で `pinnedIds` の意味が変わらないよう、シグネチャ変更の影響範囲を
  `geometry.js` / `packing.js` 内で確認する。

**確認手順**: 上記の再現手順と同じ状況（障害物にクリアランス未満で接する機材A、離れた機材B）を作り、Bだけを
ドラッグ・回転してもAの座標が変化しないことを確認する。あわせて、Aを直接ドラッグして障害物に近づけた場合は
従来どおり押し出し・棄却が機能すること（障害物の不動性そのものは壊さないこと）も確認する。
`npm test` の `geometry.test.mjs` / `packing.test.mjs` が通ることを確認する。

## 中 2: 荷台に収まらない量を自動配置すると、収まる分も含めて完全に無操作になる

**場所**: `docs/assets/js/packing.js:189` の `autoArrangeSlot()` が呼ぶ `arrangeFloor()`（`packing.js:239`）は、
実荷台（`bedOf(slot)`、仮置きゾーンを含まない）に**全点**を配置できない場合に `null` を返し、`autoArrangeSlot()` は
`status: 'failed'`（`packing.js:201`）として何も変更しない。

**症状**: 実荷台に入りきらない量の機材があるレイアウト（一部が仮置きゾーンにはみ出している状態）で自動配置を実行すると、
「全機材を収められなかったため、配置を変更しませんでした。」という通知が出るだけで、**実荷台上に既にある機材も
1点も詰め直されない**（再現スクリプトで確認: 荷台2400×5000に1200×1000の機材14点、うち実荷台に収まるのは約10点、
残り4点を仮置きゾーンに置いた状態で `autoArrangeSlot()` を呼ぶと `status: 'failed'` になり、`placements` が一切返らない）。
対照として仮置きゾーンの機材が1点だけで実荷台に収まる場合は `status: 'arranged'` となり正しく引き戻される。

**なぜ問題か**: 仕様4.2節はリアゲート側の仮置きゾーンを「実荷台をはみ出す配置も棄却されず…荷台に入りきらない機材の
逃がし先も兼ねる」「自動配置（6.2節）は実荷台の範囲だけを詰め直す」と位置づけている。つまり**積みきれない状況こそが
仮置きゾーンの本来の使いどころ**であり、「どう積むか」を検討したい場面（LoadSymの最優先事項）で自動配置が一番
必要になる状況において、機能そのものが無効化されてしまう。仕様6.2節の「全点を正常に置けた場合だけ一括で確定し、
1点でも置けない…場合は元の配置を一切変えない」の記述は保っているが、実用上は「床面に収まる分だけ詰め直し、
残りは仮置きゾーンに残す」挙動のほうが仕様の意図（4.2節）に合う。

なお現状この機能はAdmin限定の試験機能（`docs/simulator.html:121,303` の `x-if="isAdmin"`）であり、緊急度は
中程度に留めてよい。

**直し方の方針**: `arrangeFloor()` が実荷台へ全点配置できずに失敗した場合、**実荷台に収まる範囲だけを対象に
再度詰め直しを試みる**（収まらない機材は元の位置のまま、または仮置きゾーン側へ残す）フォールバックを追加する。
「どの機材を実荷台側に残すか」の選び方（面積が大きいものを優先、現在すでに実荷台にある機材を優先、等）は
既存の `arrangeFloor` の候補選定ロジック（グループ順・戦略比較）と整合させること。全点が収まらない場合に
即座に諦めるのではなく、部分成功のパスを用意する方針で実装する。

**確認手順**: 再現手順と同じ状況（実荷台に入りきらない量、一部仮置きゾーン）で自動配置を実行し、実荷台に収まる分が
きちんと詰め直され、収まらない分は仮置きゾーンに残ることを確認する。既存の `packing.test.mjs` の
`autoArrangeSlot` 関連テストが通ることを確認し、新しいフォールバック挙動のテストケースを追加する。

## 中 3: 形状エディタで新規パーツ作成時に角落とし量が前のパーツの値を引き継ぐ

**場所**: `docs/assets/js/shape-editor.js:684-693` の `pointerUp()` 内、`this.drag.kind === 'create'` 分岐。
新規パーツ作成が確定すると `this.parts.push(this.draft); this.selectedIndex = this.parts.length - 1;` で
選択対象は切り替わるが、`this.chamfers` はリセットされない。既存パーツをクリックで選択する経路
（`shape-editor.js:551` の `partPointerDown()`）は `this.chamfers = [0, 0, 0, 0];` を実行しているのに対し、
この新規作成の経路と `openEditor()`（`shape-editor.js:423-443`）にはこのリセットが無い。

**症状**: 矩形パーツを選択して角落とし欄（左下/左上/右上/右下）に数値を入力したあと、「角落とし」を押さずに
別の矩形・円・多角形を新規作成すると、選択は新パーツに移るのに角落とし入力欄には前のパーツの値が残ったまま表示される。
その状態で「角落とし」を押すと、新パーツが意図せず前のパーツと同じ量だけ角を落とされる（再現確認済み: 左下に200を
入力→新規400×400矩形を作成→角落とし実行→新パーツが左下200mmを削った5頂点の多角形になる）。

**直し方**: `pointerUp()` の `this.drag.kind === 'create'` 分岐、`this.selectedIndex = this.parts.length - 1;` の
直後に `this.chamfers = [0, 0, 0, 0];` を追加する。あわせて `openEditor()` にも保険として同じ初期化を追加する
（エディタを開いた直後に前回の値が残っていないことを保証するため）。

**確認手順**: 機材編集フォームで「形を編集」を開き、既存矩形パーツの角落とし欄に値を入力する→確定せずに新しい矩形を
ドラッグ作成する→角落とし欄がすべて0に戻っていることを確認する。`npm test` の `shape-editor.test.mjs` が通ることを
確認し、このケースのテストを追加する。

## 低 1: DBのCHECK制約違反が「寸法や重量を確認してください」という誤誘導文言になる

**場所**: `docs/assets/js/error-messages.js:19-20` の `if (/violates check constraint/i.test(message)) { return '入力値が
許容範囲外です。寸法や重量を確認してください。'; }` は、`_color_check`（15行で個別処理済み）以外の**すべての**
CHECK制約違反を同じ固定文言に丸めている。

**なぜ問題か**: 今回のクリアランス上限の不整合（`layouts_clearance_mm_check`）が実際に発生した際、この文言のせいで
「クリアランスの値が原因で保存に失敗している」ことがユーザー（Admin含む）からは分からなかった。寸法・重量以外の
列（`clearance_mm` 等）のCHECK違反でも同じ文言が出るため、原因調査を妨げる。

**直し方**: 制約名からある程度テーブル・列を推測できるメッセージにする（例: 制約名に `clearance` を含む場合は
「クリアランスの値が許容範囲外です」、それ以外は現行の汎用文言のまま）。`_color_check` の個別処理（15-17行）と
同じパターンで、正規表現を追加する形でよい。将来同種の制約が増えても保守できるよう、"制約名 → 日本語メッセージ"
の対応表を1箇所にまとめる形にすることが望ましい。

**確認手順**: クリアランスを一時的にDB側で再び範囲外にする、またはテストで `error-messages.js` の変換関数に
`layouts_clearance_mm_check` を含むメッセージを渡し、クリアランスだと分かる文言が返ることを確認する。

## 低 4: トラックフォームの障害物入力欄に `min` 属性が無い

**場所**: `docs/simulator.html:291-295`（`truckForm.obstacles` の x / y / 幅 / 奥行き入力欄）はいずれも
`<input type="number" x-model.number="...">` のみで `min` 指定が無い。DB側は `truck_obstacles` テーブルで

**確認手順**: トラックフォームで障害物のx欄に `-1` を入力しようとすると、ブラウザのネイティブバリデーションで
