## 高 1: 他ユーザーのレイアウトを開くと「複製して編集」ができない

**症状**: `docs/assets/js/pages/simulator.js:958` の `openLayout()` は、他人のレイアウトを開くと
`this.readOnly = true` にした上で「編集するには『別のレイアウトとして保存』してください」と案内する。
ところが `docs/simulator.html:46` の保存ボタンは `:disabled="readOnly || !hasContent"` になっており、
`readOnly` が true の間は保存ダイアログ自体を開けない。つまり案内文どおりの操作ができず、
Editor/Adminが他人のレイアウトを開くと実質何もできない。

**原因**: `readOnly` が2つの異なる意味（①Viewerロールだから編集不可、②他人のレイアウトだから上書き不可）を
1つのフラグに混ぜてしまっている。

**直し方の方針**:
- `docs/assets/js/pages/simulator.js:122` の `this.readOnly = !canEdit(context.profile);`（ロール由来）と、
  `openLayout()` 内で他人の行を開いたときに立てる「所有者不一致」を別々に持てるようにする
  （例: `roleReadOnly` を別プロパティにし、ドラッグ・回転・削除等の操作ガードは従来どおり
  `readOnly`（= `roleReadOnly || 所有者不一致`）を使い続けてよいが、**保存ボタンの活性判定だけ**
  `roleReadOnly` を見るようにする）。
- 他人のレイアウトを開いている間に保存ダイアログを開いた場合は、`asNew` を強制的に `true` にし、
  チェックボックス（`docs/simulator.html:346` 付近）を操作不能にする（上書き保存を選ばせない）。
  Viewerロールの場合は従来どおり保存ボタンごと無効化する（Viewerは複製もできない。仕様3.1節）。
- `docs/assets/js/pages/simulator.js:919-921` の `openSaveDialog()` / `saveLayoutNow()` に必要な分岐を追加する。

**確認手順**: Editorアカウントでログインし、他ユーザーが作成したレイアウトを一覧から開く →
保存ボタンが押せ、保存ダイアログが開き、「別のレイアウトとして保存」が強制的にオンになっていること →
保存すると自分名義の新規レイアウトとして保存され、`simulator.html?layout=` が新IDに切り替わること。
Viewerアカウントでは従来どおり保存ボタンが押せないこと。

## 高 2: レイアウト複製時に `clearance_mm` が引き継がれない

**症状**: `docs/assets/js/pages/layouts.js:169-178` の `duplicate()` が `saveLayout()` に渡すオブジェクトに
`clearanceMm` を含めていない。`docs/assets/js/layouts.js:123` の `clearance_mm: layout.clearanceMm` が
`undefined` になり、DB列の既定値（5mm）に落ちる。元のレイアウトが10mmクリアランスで組まれていても、
複製すると黙って5mmに変わり、はみ出し・干渉判定の結果が変わってしまう。

**直し方**: `duplicate()` 内で読み込んだ `row`（`loadLayout(layout.id)` の戻り値）には `clearance_mm` が
含まれている（`docs/assets/js/layouts.js:43` のSELECT列に既にある）。`saveLayout()` へ渡すオブジェクトに
`clearanceMm: row.clearance_mm ?? DEFAULT_CLEARANCE_MM` を追加する。`DEFAULT_CLEARANCE_MM` は
`docs/assets/js/pages/layouts.js:14` で既にimport済み。

**確認手順**: クリアランスを10mm以外（例: 15mm）に設定して保存したレイアウトを、レイアウト一覧の
「自分用に複製」（他人のレイアウト）または自分のレイアウトの複製で複製し、複製後のレイアウトを開いて
クリアランス設定欄が元と同じ値になっていることを確認する。

## 高 3: 形状エディタの「閉じる」が編集を破棄しない

**症状**: `docs/assets/js/shape-editor.js` はパーツ移動・削除・角落とし・回転などの操作のたびに
`syncForm()` を呼び、機材フォームの `shape` / `width_mm` / `depth_mm` を即座に書き換える
（呼び出し箇所は `updatePart` / `applyChamfer` / `rotatePart` / `insertVertex` / `removeVertex` /
`finishPolygon` / `pointerUp` 内の移動・新規作成確定など多数）。一方 `closeEditor()`（435-441行）は
エディタ内部のUI状態（`drag` / `draft` / `activeVertex` 等）をリセットするだけで、フォーム側の値は
一切元に戻さない。`docs/partials/equipment-form.html` の234-235行付近では「形を反映」（`apply()`）と
「閉じる」（`closeEditor()`）が別ボタンとして並んでおり、ユーザーは「閉じる」＝編集前の状態に戻ると
期待するが、実際には編集がそのまま確定した状態でエディタだけが閉じる。

**直し方の方針**: `openEditor()` を呼んだ時点の `form.shape`（および `width_mm` / `depth_mm`）の
スナップショットを保持しておき、`closeEditor()` ではそのスナップショットへ `form` を復元してから
UI状態をリセットする。「形を反映」（`apply()` があれば）を押した場合はスナップショットを更新して
確定、という一般的な「編集ダイアログのキャンセル」パターンにする。
`equipment-form.html` 側のボタン配置・ラベルは変更不要（「閉じる」の意味が仕様通りになるだけ）。

**確認手順**: 機材編集フォームで「形を編集」を開き、既存パーツを1つ削除する → 「閉じる」を押す →
フォームの幅・奥行き入力欄と保存されるshapeが編集前の状態のままであることを確認する。
逆に「形を反映」を押した場合は編集後の状態が反映されることも確認する。

## 中 2: `pointercancel` を `pointerup` と同一ハンドラで処理している

**場所**: `docs/assets/js/pages/simulator.js` のドラッグ処理（`onUp` 関数、`pointerup` と
`pointercancel` の両方に登録されている）。`pointercancel` はOS操作の割り込み等でドラッグが強制中断
されるイベントで、その時点の `clientX/clientY` は意味のある着地点とは限らない。現状は通常の
ドロップ処理（同一エリア内スナップ／エリア間移動）がそのまま走ってしまう。

**直し方**: `pointercancel` 専用のハンドラを用意し、`placement.x = start.x; placement.y = start.y;`
（掴む前の位置に戻す）だけを行い、スナップ・エリア間移動の判定はスキップする。

**確認手順**: 実機での再現は難しいため、コードレビューで `pointercancel` 時にドロップ判定を通らず
元の位置に戻る分岐になっていることを確認すればよい。

## 低 1: `insertVertex` の丸めが厳密な共線判定と食い違う場合がある

**場所**: `docs/assets/js/shape-editor.js:803-825`。辺の中点座標を `roundMm()` で100mm/10mm単位に
丸めてから頂点として挿入するため、辺の長さによっては丸め後の中点が両隣の頂点と厳密には共線に
ならないことがある（例: 整数座標 `(0,0)-(7,3)` の中点 `(3.5,1.5)` は丸めで `(4,2)` になり、
`(0,0)-(4,2)-(7,3)` の外積はゼロにならない）。`isConvex` はこの場合を「凹形状」と誤判定し、
本来通ってよい辺への頂点追加が「短すぎて頂点を追加できません」と拒否される可能性がある
（逆に通った場合も、コメントが前提とする「中点は両隣と一直線に並ぶ」が崩れる）。

**直し方**: 丸め後の座標が両隣と共線になるかどうかを実際にチェックし、共線が崩れる場合は
丸めない座標（またはグリッドに吸着させつつ最も近い共線点）を使うよう調整する。厳密な数学的整合性より
実用上の挙動を優先し、影響範囲は小さいため、対応が難しければ最後に見送ってもよい
（その場合はこのプロンプトの「やらないこと」に明記して報告すること）。

**確認手順**: 座標がグリッド吸着後も非共線になりやすい斜め辺（例: 幅700mm/奥行き300mmの矩形を
角落としで台形にしたのち、斜辺に頂点追加）で、頂点追加が意図通り成功する／拒否メッセージが
出ないケースが増えることを確認する。

## 低 3: CSVインポートのカテゴリ不一致警告文言が実際のフォールバック先と食い違うことがある

**場所**: `docs/assets/js/csv.js:172-178` の警告文言 `` `カテゴリ「${categoryName}」が見つかりません
（その他として取り込みます）` `` は固定文言。実際のフォールバック先は呼び出し元
（`docs/assets/js/pages/admin.js` の `previewCsv` が渡す `this.defaultCategoryId`、
実体は `equipment-form.js` の `defaultCategoryIdOf`）で決まり、「その他」という名前のカテゴリが
存在すればそれ、無ければ**先頭のカテゴリ**が使われる。「その他」カテゴリを削除・リネームした運用では、
警告文言と実際の取り込み先カテゴリ名が一致しなくなる。

**直し方**: `parseCsv`（または呼び出し元）に実際のフォールバック先カテゴリ名を渡し、
警告文言を `` `カテゴリ「${categoryName}」が見つかりません（「${fallbackCategoryName}」として
取り込みます）` `` のように動的に生成する。

**確認手順**: 管理画面のカテゴリタブで「その他」カテゴリを一時的にリネームし、存在しないカテゴリ名を
含むCSVをプレビューする → 警告文言が実際に使われるカテゴリ名と一致することを確認する
（確認後、カテゴリ名は元に戻すこと）。

## 低 4: 自動配置の細部非最適（戦略の使い回し・押し出し方向の固定）

**場所1**: `docs/assets/js/packing.js` の `autoArrangeSlot()`。既存配置（`originals`）を採用した場合
（再計算より使用奥行きが短いとき）でも、続く `findStackSuggestion(originals, normal, bed, obstacles,
clearanceMm, recalculated.strategy)` には常に「フル再計算で勝った戦略」を渡している。既存配置は
どの戦略でも生成されていない人手配置のため、縦積み提案の `core` 再配置に無関係な戦略が使われ、
saving計算がやや不利に出る場合がある。

**場所2**: `docs/assets/js/geometry.js` の連鎖押し出し（`pushDirection` / `lockedAxis` まわり、
557-608行、662-665行）。一度押し出された機材は以後その軸方向にしか動かさない仕様（振動防止）のため、
密集した配置で本来の回避方向がロック済み軸と異なる場合、`settle()` の差分検証によって操作自体が
棄却されることがある（誤って確定はしないが、理由が分かりにくいまま回転操作が弾かれる）。

**直し方**: どちらも実害は小さく、`settle()` の安全網（差分判定・反復上限）で最終的な不正配置には
ならない。優先度は低いため、以下のいずれかで対応する。
- 場所1: `normal === originals`（既存配置採用）のときは `findStackSuggestion` に渡す戦略を
  再計算せず全戦略で軽く試す、または `bestStrategy` 引数をoptionalにしてnull時は内部で複数戦略を
  試すようにする。
- 場所2: 対応を見送ってよい。ロールバックで安全性は担保されているため、今回は
  「密な配置で理由不明の回転棄却が頻発する」という利用者からの報告があった場合にのみ着手する方針で、
  このプロンプトでは**コメントで注意点を明記する程度に留め、ロジックは変更しない**。

**確認手順**: 場所1のみ修正する場合、同一機材5台以上・既存配置が採用されるレイアウトで自動配置を
実行し、縦積み提案の内容が変わらない（または改善する）ことを確認する。`npm test` の
`packing.test.mjs` が通ることを確認する。
