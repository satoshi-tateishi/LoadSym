# 自動配置 ステップ1 実装プロンプト（回転の探索と複数戦略の比較）

`project-docs/AUTO_LOAD.md` の §6「今後の調整候補」のうち、**DB変更を伴わない範囲**を実装する。
対象は `docs/assets/js/packing.js` の `autoArrangeSlot()` 周辺のみ。成功配置パターンDB（§9）は**この作業では作らない**。

## なぜ今これをやるか（計測結果）

着手前に現行実装を実測した。判断の根拠なので、実装中も同じ数値で比較すること。

**A型（`tests/packing.test.mjs` の「積み込みテスト」構成 / 18点 / 荷台 2363 × 9090mm）**

| | 使用奥行き |
|---|---|
| 人手の理想配置 | 3185mm |
| 現行実装（人手が付けた向きのまま） | **3295mm**（理想比 +3.5%） |
| 現行実装（全機材を0度にして投入） | **3580mm**（理想比 +12.4%） |
| 総床面積 ÷ 荷台幅（到達不能な下限） | 2971mm |

**その他の実測値**

| ケース | 使用奥行き | 実行時間 |
|---|---|---|
| B型 20点（`status` は `unchanged`、core 3530mm、候補 `upaar-2`） | 全体 4667mm | 10ms |
| 5種類×4点の20点 | 3014mm | 3ms |
| 30点 | 4565mm | 47ms |
| 40点 | 5950mm | 70ms |
| 60点 | 8616mm | 459ms |

読み取れること。

- 使用奥行きという尺度では、現行実装は既に人手の理想の3.5%以内にある。**大きく作り直す必要はない。**
- 一方で **投入時の向きだけで285mm（8.6%）変動する**。`compactGroup()` が現在の `rotation` を固定しているため、
  ユーザーが機材を置いたときの向きがそのまま結果の良し悪しになっている。これが単一で最大のレバー。
- グローバルな回転戦略（全て0度 / 全て90度 / 長辺を幅方向へ など5種）を試して最良を採る実験では**改善がゼロ**だった。
  理想配置は機材ごとに向きが混在するため、荷台全体を一律に回しても意味がない。**回転はグループ単位で決めること。**
- 素朴なper-item回転付きBLFを別実装して比較したところ 3625 / 3685mm で、**現行のブロック方式のほうが良かった**。
  `compactArrangementGroups()` によるブロック化は正しい方向なので、これは壊さないこと。

## 必須実装1: グループ単位の回転探索

`docs/assets/js/packing.js` の `compactGroup()`（現在 434行目付近）は、渡された placement の `rotation` を
そのまま使ってブロックを組んでいる。ここに**ブロックごと90度回した候補**を足す。

- 候補は「現状の向きのまま」と「グループの全メンバーの `rotation` に +90 した向き」の2つ。
  全メンバーに同じ量を足すので、A型の UPA-1C（`[0, 180, 0, 90]`）のような**混在した向きの相対関係は保たれる**。
- 回転しても外形が変わらないグループは重複評価しない。判定は寸法で行う
  （そのグループの全メンバーについて `boundsOf(toParts(p))` の `w`/`d` が `rotation` と `rotation + 90` で
  一致するなら、円・正方形なので候補を増やさない）。形状の種類（`shape.kind`）で分岐しないこと。
  L字などの複合形状は外形が変わるので、必ず両方試す。

**向きをグループ内で決めてはいけない。** 実測で、グループ内の奥行き最短で回転を選ぶとA型は4230mm以上に退行した。
奥行きが最短のブロックが、他のブロックと組み合わせやすい形とは限らないため。`compactGroup()` は
**勝者を1つ返すのをやめ、ブロック候補の配列を返す**こと。選択は必須実装3で全体を見て行う。

これは §3.4 が回転を見送った理由（「並び順と向きのどちらが結果を悪くしたか切り分けにくい」）に反するように見えるが、
**グループ単位に限定すれば切り分けは可能**なので、そこは方針を変える。AUTO_LOAD.md の §3.4 も更新すること。

## 必須実装2: 幅の比率も候補にする（勝者を選ばない）

`compactGroup()` の以下は、A型・B型に合わせて手で決めた定数になっている。

```js
const preferredRatio = placements.length === 2 ? 2 / 3 : 3 / 5;
const preferredMax = Math.max(largestWidth, Math.floor(bed.w * preferredRatio));
```

**これは「グループの点数に応じて比率を変える」ルールである点に注意すること。** A型は2点グループと4点グループが
混在するため、現行の挙動は「2点は2/3、他は3/5」という組み合わせであり、**単一のグローバル比率では再現できない**。
グローバル比率に置き換えると現行の解が探索空間から消え、A型は3295mm → 3585mm に退行する（実測済み）。

したがって比率も**グループごとの候補**にする。必須実装1の回転候補との直積を作り、
`(width, depth)` が同じ候補は重複排除する。比率の候補は `[1/2, 3/5, 2/3, 1]` を初期値とする
（`1` を含めるのは、CL5 のような幅広機材で荷台幅を使い切るのが最善になる構成を捨てないため）。

`compactGroup()` の戻り値はこの候補配列になる。ここでも**選ばない**。

## 必須実装3: 部分配置の評価で候補を選び、並び順を掃引する

現行は `arrangeFloor()` が単一の並べ方しか試していない。**完成した配置同士を比較して選ぶ**方式にする。
`findFreeSpot()` の内部や `geometry.js` は変更しないこと。当たり判定を二重実装しない方針は維持する。

### 候補の選択は「部分配置の評価」で行う

各グループの向きと比率を全体の完成配置で比較したくなるが、素直にやるとグループ数の指数（A型は7グループで
2^7 × 比率4 通り）になり破綻する。**`arrangeGroups()` がグループを順に置く既存の流れの中で決めること。**

グループを1つ置くとき、そのグループの全候補を `findFreeSpot()` に通し、
**その時点までに置いた全機材を含む状態**で次の順に比較して最良を採る。

1. 置いた全体の使用奥行き（`usedDepth()` 相当）が小さい
2. そのブロックの後端（`y + d`）が小さい
3. 候補の定義順（現状の向き・現行の比率を先に定義すること）

これで計算量は `O(グループ数 × 候補数)` に収まる。候補は重複排除後で8個程度なので、
現行のグループごと1回が8回になるだけで済む。

### 戦略の掃引は「グループの並び順」だけ

向きと比率が上で決まるので、比率×並び順の12戦略は不要。並び順3種だけを掃引する。

- 現行の `totalArea` 降順
- `depth` 降順
- `width` 降順

現行の `arrangeIndividually()` は今までどおり**全戦略が失敗したときのフォールバック**として残す。

### 退行しないことを設計で保証する

**戦略配列の先頭に「現行実装をそのまま再現する戦略」を置くこと。** 内容は次のとおり。

- 比率 = 現行のルール（2点グループなら 2/3、他は 3/5）
- 回転 = 現状維持
- 並び順 = `totalArea` 降順
- **グループごとの候補探索をしない**（現行と同じく1候補で決め打つ）

最終選択は完成した配置同士の比較なので、この戦略が常に候補に入っていれば、**結果が現行以上であることが
構造的に保証される**。退行が観測されたら、それは実装ではなく選択ロジックのバグとして切り分けられる。
この保険を外さないこと。

### 評価関数

全戦略の結果を次の順で比較し、最良の1つを採る。**同点解消まで決まり切った順序にすること**（決定性の担保）。

1. 全点を配置できたか。`findInvalidShapes()` が0件か。**満たさない候補は比較に入れない**
2. `usedDepth()` が小さい
3. 同一グループのまとまり（各グループの外接矩形面積の合計が小さい）。
   同じ奥行きなら、同じ機材が散らばっていないほうを採る
4. 戦略の定義順（先に定義したほうを採る＝同点なら現行実装が勝つ）

**リアゲート側のツライチ評価は今回入れない。** AUTO_LOAD.md §6.1 のとおり、どの辺を揃えるべきかが実データで
未確認のため。推測で評価式に入れると、後で「なぜこの配置になったか」が説明できなくなる。

### 計算量の上限

現行は60点で459ms（うち大半は `findStackSuggestion()` が `arrangeFloor()` を候補ごとに呼び直す分）。
**点数に応じた上限を設けること。**

- 目安: 20点で300ms以内、60点で1500ms以内
- 実装は「点数が閾値を超えたら戦略配列の先頭N本だけ使う」で良い。閾値とNは実測して決め、
  **なぜその値かをコメントに残すこと**
- `findStackSuggestion()` は候補ごとに `arrangeFloor()` を丸ごと呼び直している（現在275行目付近）。
  戦略を増やすとここが乗算で効くので、**縦積み候補の探索では戦略を1本（最良戦略）に固定する**こと

## 必須実装4: テストの追加と既存テストの扱い

`tests/packing.test.mjs` に少なくとも次を足す。

- グループ単位の回転で、全機材を0度で投入したA型が現行の3580mmより改善すること
- 円・正方形のグループでは回転候補を増やさない（結果の `rotation` が変わらない）こと
- 複数回実行して完全に同じ結果になること（既存の決定性テストと同じ形式）
- 入力の slot / placements / snapshot を破壊しないこと（既存テストの範囲を回転探索にも広げる）
- 戦略上限に掛かる点数（60点程度）でも `status` が `arranged` になり、要確認が0件であること

**既存テストが落ちたときの扱いに注意すること。**

- `'積み込みテスト型の使用奥行きを理想に近づける'` は現在 `usedDepth <= 3350`（実測3295mm）。
  改善後は**3295mm以下**を維持すること。これを超えたら退行なので直す
- `'B型ではUPA-ARを1台だけ縦積み候補にする'` は `status: 'unchanged'` を期待している。これは
  「人手のB型配置のほうが再計算より短かった」という意味なので、**改善の結果 `arranged` に変わるのは退行ではない**。
  その場合はテストを更新してよいが、要確認0件は必ず維持すること
- **縦積み候補そのものが消えるのも、それ自体は退行として扱わない。** 床面配置が十分に短くなれば
  「1台外しても250mm / 10%は縮まない」となり、提案が消えるのは論理的に正しい挙動である。
  ただし**黙って消さないこと。** 消えた場合は `findStackSuggestion()`（`packing.js:275` 付近）の
  `normalDepth` / `coreDepth` / `saving` の実測値を報告に書くこと。閾値（同 `:299` の250mm・10%）を
  調整すべきかの判断材料にする。実装のほうを歪めて候補を復活させないこと
- それ以外の既存テストが落ちた場合は**実装の退行**として扱い、テストを緩めないこと

`npm test` は現在 240件（geometry 92 / packing 138 / shape-editor 10）すべて通っている。追加後も全件通すこと。
