# 自動配置（一括パッキング）実装計画

## 1. 目的

シミュレーターで選んだ1台のトラックについて、そのトラック内に既にある機材を、荷台の左前から自動で詰め直す。

最初から最適解を求めるのではなく、既存の配置判定を再利用した単純で予測しやすいロジックを先に実装し、実際の音響機材データで動作を確認してから、並び順・回転・ラッシングを意識した整列を段階的に調整する。

現在は初版の個体配置を実装・検証した後、「積み込みテスト」の理想型を基準に同一機材のブロック配置まで調整済みである。
「積み込みテストB」については、UPA-AR 1台を床面計算から外し、他機材への縦積み候補として通知する比較ロジックを追加した。
実際の高さ方向配置や積み先の自動決定は行わない。

## 2. 現在のプロジェクトに合わせた前提

- 実装は素の JavaScript（ES Modules）で行う。TypeScript や新しい依存ライブラリは追加しない。
- 配置データは `equipments = [{ width, depth, x, y }]` ではなく、現在の `slot.placements` をそのまま扱う。
  - `placement = { id, equipmentId, snapshot, x, y, rotation }`
  - 寸法・重量・色・複合形状は `snapshot` に保存されている。
- 座標は確定仕様どおり、荷台の左前を `(0, 0)`、`x` を幅方向、`y` を奥行き方向とする。SVG上の横向き表示への変換は `renderer.js` に任せ、自動配置ロジックには持ち込まない。
- 対象はユーザーが操作したトラック1台のみとする。機材置き場、別のトラックとの間で機材を自動移動しない。
- 機材置き場は自動配置の対象外とする。置き場は積み込み前の作業台であり、荷台とはクリアランス・はみ出しの規則が異なるため。
- Viewer は実行できない。Admin / Editor でも、他ユーザーのレイアウトを読み取り専用で開いている間は実行できない。
- 高さと重量は配置順・成否に使わない。パイロット版は確定仕様どおり床面積ベースとする。既存の高さ超過・最大積載重量の警告表示は配置後もそのまま利用する。
- DB変更は不要。自動配置の結果は通常の `placements` として既存のレイアウト保存処理に渡す。

## 3. 初版の仕様

### 3.1 操作対象

- 各トラックの見出しに「自動配置」ボタンを置き、そのトラック内の全機材を対象にする。
- トラックに機材がない場合、または読み取り専用の場合はボタンを無効にする。
- 現在の機材置き場や選択中の機材だけを対象にする機能は初版には含めない。

トラックごとのボタンにするのは、最大3台を同時表示できる画面で対象を取り違えないためである。

### 3.2 検証後に採用した配置ロジック

既存の `geometry.js` にある `findFreeSpot()` を再利用し、次の順で決定的に配置する。

1. 対象トラックの placements を複製し、元配列・元オブジェクトを変更しない。
2. 各機材について現在の `rotation` を反映した外形 bbox を求める。
3. `equipmentId`（無い場合は同一スナップショット）ごとにまとめ、同一機材の小さなブロックを作る。各ブロックは現状向きと全員を90度回した向き、幅比率 1/2・3/5・2/3・1 を候補にする。円・正方形など回転しても全メンバーの外形寸法が変わらない場合は回転候補を増やさない。
4. 退行防止のため、変更前と同じ「現状向き、2点なら幅2/3・それ以外は3/5、面積順」の戦略を必ず先頭で実行する。探索戦略では面積・奥行き・幅の3種類のグループ順を比較する。
5. 探索戦略はグループを置くたびに全候補を `findFreeSpot()` へ通し、その時点の全体使用奥行き、置いたブロックの後端、候補定義順の順で選ぶ。ブロック単体の奥行きだけでは向きを決めない。
6. 外形の奥行き・幅が大きい個体から置く初版方式も、フォールバックではなく**対等な候補**として必ず比較する。変更前はグループ配置が最終検証で落ちたときにこの方式が採用されており、点数の多い構成ではこれが最良解になる。候補から外すと変更前に到達できていた解が消えて退行する。
7. 全点を置いた後、既存の `findInvalidShapes()` で荷台境界・障害物・機材間のクリアランスを最終検証する。`findFreeSpot()` の探索結果だけで成功と決めない。
8. 成立した完成配置は、使用奥行き、同一グループの外接矩形面積合計、戦略定義順で比較する。同じ奥行きならグループ配置を優先する。既存配置も正常で完成配置より短ければ理想型として保持する。
9. 1点でも置けない場合や最終検証で不正が見つかった場合は途中結果を採用せず、元の placements をそのまま返す。

返却配列は描画・保存への不要な影響を避けるため元の順番に戻す。自動回転はグループ単位に限り、搬出順とリアゲート側のツライチ評価はまだ行わない。41点以上は実測した操作待ち上限を守るため、退行防止と面積順探索の先頭2戦略に制限する。縦積み候補の再計算は、通常配置で勝った1戦略だけを使う。

### 3.3 縦積み候補の提案

- 同一機材が5台以上ある場合に限り、1台ずつ除外した床面配置も比較する。
- 除外により使用奥行きが10%以上かつ250mm以上短くなり、残りの全機材が正常なら候補とする。
- 除外した1台は削除せず、床面配置の後方に単独で残す。既存の正常な退避位置があれば保持する。
- UIでは「1台は床面計算から外しています。他の機材への縦積みを検討してください」と機材名付きで通知する。
- `stack_level`、高さ、耐荷重、積み先は変更・決定しない。パイロット版では提案だけに留める。

### 3.4 グループ単位の自動回転

- 同一機材グループの全メンバーへ一律に90度を足す候補を作る。混在した向きの相対関係とブロック内の相対位置は保つ。
- 向きはブロック単体の奥行きでは決めず、その時点までに置いた全機材を含む部分配置で比較する。短いブロックが他ブロックと組み合わせやすいとは限らないためである。
- 円・正方形など、全メンバーの外形寸法が90度回転前後で同じなら重複候補を作らない。形状種別ではなく外形寸法で判定する。
- per-itemの自由回転は行わない。同一機材の向きがばらつき、既存ブロック方式より実測結果も悪かったためである。

初版で回転を見送った理由は、並び順と向きの影響を切り分けにくかったためである。現在はグループ単位の候補と名前付き戦略に限定し、どの段階で選ばれたかを決定的に再現できるため、この方針を変更した。

### 3.5 失敗時の扱い

汎用案にある `isOverflow = true` は追加しない。現在の確定仕様では、通常操作によって荷台からはみ出す配置を新たに成立させず、収まらない操作を棄却するためである。

自動配置も同じ方針に揃え、全点を配置できなければ次のように扱う。

- 座標と回転を一切変更しない。
- 置けなかった placement ID を計算結果に含める。
- UIでは「全機材を収められなかったため、配置を変更しませんでした」と通知する。
- 既存データに赤い機材がある場合でも、自動配置の途中結果で状態を悪化させない。

### 3.6 純粋関数のインターフェース

`docs/assets/js/packing.js` に、DOM・Alpine・Supabaseを参照しない関数を追加する。

```js
export function autoArrangeSlot(slot, clearanceMm = DEFAULT_CLEARANCE_MM) {
  // 成功:
  // { placements: [...], status: 'arranged', unplacedIds: [] }
  // 座標が初めから同じ:
  // { placements: slot.placements, status: 'unchanged', unplacedIds: [] }
  // 縦積み候補がある場合は上記へ次を追加:
  // { stackSuggestion: { placementId, name, coreUsedDepthMm } }
  // 失敗:
  // { placements: slot.placements, status: 'failed', unplacedIds: [...] }
}
```

関数名を `autoArrangeEquipments(equipments, truckWidth, truckDepth)` にしないのは、現在の当たり判定に必要な `rotation`、`snapshot.shape`、障害物、トラック寸法、クリアランスが `slot` にまとまっているためである。

純粋関数の責務は座標計算だけに限定し、履歴への追加、通知、再描画はページ側で行う。

## 4. UIへの接続

`docs/assets/js/pages/simulator.js` にトラックのスロット番号を受け取るハンドラを追加する。

```js
autoArrange(slotNumber) {
  if (this.readOnly) return;

  const slots = this.rawSlots();
  const slot = slots.find((item) => item.slot === slotNumber);
  if (!slot || isStaging(slot) || slot.placements.length === 0) return;

  const result = autoArrangeSlot(slot, this.clearanceMm);
  if (result.status === 'failed') {
    this.notice('全機材を収められなかったため、配置を変更しませんでした。');
    return;
  }
  if (result.status === 'unchanged') {
    this.notice('機材は既に自動配置と同じ位置にあります。');
    return;
  }

  slot.placements = result.placements;
  this.commit(slots);
  this.notice(`${slot.truck.name} の機材を自動配置しました。`);
}
```

空配列・同一座標・失敗は `status` で区別し、不要な履歴を追加しない。成功時は既存の `commit()` を1回だけ呼ぶ。これにより、全機材の移動が履歴上の1操作になり、「元に戻す」で自動配置前へ一度に戻せる。`commit()` 後の再描画には既存の `renderAll()` を利用する。

ボタンには既存のTailwindクラスを優先して使う。新しいクラスを追加した場合は `npm run build:css` を実行し、生成された `docs/assets/css/styles.css` もコミット対象にする。

## 5. 実装手順

### フェーズ1: 最小ロジック

1. `packing.js` に `autoArrangeSlot()` を追加する。
2. `toParts()` / `toShape()` / `boundsOf()` / `findFreeSpot()` / `obstacleShapes()` を再利用し、当たり判定を二重実装しない。
3. 同一機材グループ単位の90度回転候補を含め、左前から配置する。
4. 配置後に `findInvalidShapes()` で全体を検証する。
5. 全点配置できない場合や検証に通らない場合は原状維持にする。

### フェーズ2: ユニットテスト

`tests/packing.test.mjs` に少なくとも次を追加する。

- 空のトラックでは変更しない。
- 矩形機材を奥行きの大きい順に左前から配置する。
- 入力の slot / placements / snapshot を破壊しない。
- 円・正方形では回転を維持し、外形が変わるグループでは90度回転候補も検証する。
- ユーザー設定のクリアランスを確保する。
- 荷台幅いっぱいに近い機材では、既存の壁クリアランス例外と同じ結果になる。
- 障害物を避ける。
- L字・円・凸多角形を既存の厳密形状判定で配置できる。
- 全点が入らない場合は途中結果を返さず、元座標を維持する。
- 同寸法の機材で毎回同じ結果になる（安定した決定性）。

ロジック変更後に `npm test` を実行し、geometry / packing / shape-editor の既存テストもすべて通す。

### フェーズ3: UI接続

1. `simulator.js` から `autoArrangeSlot()` を読み込む。
2. `autoArrange(slotNumber)` を追加し、成功時だけ `commit()` する。
3. `docs/simulator.html` の各トラック見出しへ「自動配置」ボタンを追加する。
4. 読み取り専用・空トラックでは無効化する。
5. 成功・失敗を既存の一時通知で知らせる。

### フェーズ4: ブラウザでの動作確認

AGENTS.md の手順どおり、ローカルサーバーは次のコマンドでポート8090に固定して起動する。

```bash
npm run serve
```

ブラウザではESモジュールのキャッシュを無効化するか、ハードリロードして確認する。

確認項目:

- トラック1台と3台の両方で、押したトラックだけが変わる。
- 機材置き場の配置は変わらない。
- 矩形・L字・円・多角形、回転済み機材、障害物ありのトラックで重なりが発生しない。
- 設定したクリアランスが反映される。
- 自動配置後に要確認件数が増えない。
- 1回のUndo / Redoで、自動配置前後を往復できる。
- 自動配置後に保存し、再読込して同じ配置が復元される。
- 入りきらない場合に元の配置が変わらない。
- Admin / Editor では実行でき、Viewerおよび他ユーザーの読み取り専用レイアウトでは実行できない。
- PNG出力・印刷にボタンや通知が写り込まない。

## 6. 今後の調整候補

グループ単位の90度回転、幅比率候補、面積・奥行き・幅による並び順比較は実装済みである。今後は実データで問題が観測されたものだけを次の順で追加する。

1. **行・列の整列評価**
   - 単に最初に見つかった空きへ置くのではなく、行の終端の凹凸、残り幅、使用奥行きをスコア化する。
   - リアゲート側のラインを揃える要件は、どの辺を揃えるかを実データで確認してから評価式へ加える。
2. **回転・幅候補の評価改善**
   - 現在は部分配置の使用奥行きとブロック後端で決めている。空きの分断など別の尺度は、実例で必要性を確認してから追加する。
3. **戦略上限の再計測**
   - 機材点数や形状構成が増えた場合は、20点300ms・60点1500msを目安に閾値と戦略数を再調整する。

## 7. 初版では行わないこと

- 機材置き場からトラックへの自動積み込み
- 複数トラックへの自動振り分け
- 高さ方向の段積みの自動確定（候補の通知だけは行う）
- 最大積載重量を考慮した振り分け
- 機材カテゴリ、搬出順、重量物の位置、ラッシングポイントなどの業務ルール
- ミリ秒単位で最適解を探索する外部パッキングライブラリの導入
- DBスキーマや保存形式への自動配置専用フィールドの追加

これらは単純な配置ロジックの実地結果と、現場で優先すべき条件が確認できてから別フェーズとして仕様化する。

## 8. 仕様書の更新

実装時には `project-docs/SPECIFICATION.md` の「6.2 配置とスナップ」または「6.6 操作補助」に、少なくとも次を追記する。

- 自動配置の対象は指定したトラック内の全機材であること。
- 機材置き場と他トラックには影響しないこと。
- グループ単位の90度回転候補、現在のクリアランス、障害物を考慮すること。
- 全機材が収まる場合だけ確定し、失敗時は原状維持すること。
- 1回のUndoで元へ戻せること。

並び順や自動回転を調整した場合も、確定した挙動に合わせて同仕様書を更新する。

## 9. 成功配置パターンDBの実装案

### 9.1 目的と基本方針

人手で作成し、要確認0件になった良好な配置を「成功パターン」として蓄積する。自動配置時には、機材名の一致だけでなく
各機材の外形寸法・形状・合計床面積・使用幅・使用奥行きが近いパターンを検索し、現在の機材へ割り当て直す。
これにより、機材名が異なっていても寸法がほぼ同じなら、過去の良い積み方を再利用できるようにする。

この仕組みは機械学習ではなく、Adminが品質を確認した事例を使う「事例ベース」の決定的な検索とする。登録数が増えても
結果を説明・再現でき、候補が成立しない場合は現在のブロック配置へ必ず戻せる構成にする。

初期段階では次を原則とする。

- 成功パターンの登録・編集・無効化・削除はAdminだけが行える。
- 有効なパターンの参照と自動配置での利用は、ログイン中の全ロールに許可する。
- 自動で全レイアウトを学習対象にせず、Adminが明示的に登録した配置だけを共有資産にする。
- パターンの座標や機材寸法を拡大縮小しない。実寸の機材を候補スロットへ割り当て直す。
- パターン適用後も `findInvalidShapes()` で通常と同じ最終検証を行う。
- パターン候補が無い、割り当てられない、または検証に通らない場合は、現在の `autoArrangeSlot()` を使う。

### 9.2 DB設計

DBマイグレーションは `project-docs/sql/009_packing_patterns.sql` とし、ファイル先頭に変更理由を日本語で記載する。
初版は検索用の集計値を通常カラム、個々の配置を `jsonb` に持つ1テーブル構成にする。登録時の1回のINSERTで
パターン全体を確定でき、親子テーブルの一部だけが保存される状態を避けられるためである。

`packing_patterns` の案:

| 列 | 型 | 用途 |
|---|---|---|
| `id` | uuid | 主キー |
| `name` | text | Adminが付けるパターン名 |
| `note` | text | 適用条件や現場上の注意 |
| `truck_width_mm` / `truck_depth_mm` | int | 登録元の荷台内寸 |
| `used_width_mm` / `used_depth_mm` | int | 機材群の外接範囲。別トラックへ収まるかの一次判定に使う |
| `total_area_mm2` | bigint | 実形状の床面積合計 |
| `item_count` | int | 機材点数 |
| `clearance_mm` | int | 登録時のクリアランス |
| `dimension_signature` | jsonb | 向きを反映した幅・奥行き・形状分類を決定的に並べた検索用署名 |
| `items` | jsonb | 個々の寸法、相対座標、回転、形状、配置用途 |
| `fingerprint` | text | 同一内容の重複登録防止用ハッシュ。unique制約を付ける |
| `active` | boolean | 削除せず検索対象から外すためのフラグ |
| `created_by` | uuid | 登録したAdmin。`profiles.id` を参照する |
| `created_at` / `updated_at` | timestamptz | 管理用時刻 |

`items` は少なくとも次の情報を持つ。

```js
{
  sourceEquipmentId: '...',       // 完全一致時の加点用。検索の必須条件にはしない
  sourceName: 'UPA-AR',           // Adminが内容を確認するための表示用
  widthMm: 535,
  depthMm: 690,
  shape: null,
  shapeClass: 'rect',             // rect / circle / polygon / compound
  areaRatio: 1,                   // 実面積 ÷ 外形bbox面積
  x: 0,                           // パターン外接範囲の左前を原点にした相対座標
  y: 0,
  rotation: 0,
  placementMode: 'floor'          // floor / stack_suggestion
}
```

`source_layout_id` や元のplacement IDには依存させない。元レイアウトの削除・上書き後も成功パターンを再現できる
独立したスナップショットにする。障害物がある荷台のパターンは初版では登録対象外とし、必要性を確認してから
障害物署名を追加する。

### 9.3 RLSと権限

`packing_patterns` ではRLSを有効にし、アプリの表示制御だけに依存しない。

| 操作 | 条件 |
|---|---|
| SELECT | `current_user_role() is not null` |
| INSERT | `current_user_role() = 'Admin'` かつ `created_by = auth.uid()` |
| UPDATE / DELETE | `current_user_role() = 'Admin'` |

シミュレーターの「成功パターンとして登録」ボタンは `x-if="isAdmin"` でAdmin以外のDOMから除外する。
Editor / ViewerがSupabase APIを直接呼んでも書き込めないことをRLSテストで確認する。

### 9.4 登録処理

複数トラックがあるレイアウトでは、対象トラックごとに1パターンとして登録する。登録ボタンを各トラックの見出しへ置き、
Adminが名前と備考を入力して確定する。

登録可能条件:

- 対象トラックに1点以上の機材がある。
- `findInvalidShapes()` による要確認が0件である。
- 荷台からのはみ出し、重なり、クリアランス不足がない。
- 初版では障害物がない。
- `floor` の機材が1点以上ある。
- 同じ `fingerprint` の有効・無効パターンがまだ存在しない。

登録時に全機材の外接範囲を求め、その左前を `(0, 0)` とした相対座標へ正規化する。`used_width_mm`、
`used_depth_mm`、`total_area_mm2`、`item_count`、`dimension_signature` はクライアントで同じ純粋関数から計算し、
画面表示とDB保存で値がずれないようにする。

Bパターンのように縦積み候補を含む場合は、床面計算から外した1台を `placementMode: 'stack_suggestion'` として保存する。
適用時も実際には段積みせず、現在と同じ縦積み提案を表示する。

### 9.5 類似パターンの検索

検索は「DBで粗く絞る」「ブラウザで詳細比較する」の2段階に分ける。GitHub Pagesの静的構成を維持し、
初版ではEdge Functionや外部検索サービスを追加しない。

DBでの一次候補:

1. `active = true`。
2. `item_count` が一致する。
3. `total_area_mm2` が対象の概ね±10%以内である。
4. `used_width_mm + 左右のクリアランス` が対象トラック幅以内である。
5. `used_depth_mm + 前後のクリアランス` が対象トラック奥行き以内である。
6. 一次候補はスコア計算前に最大50件へ制限する。

ブラウザでの詳細比較:

1. 現在の各機材とパターン内の各スロットについて、幅・奥行きの相対誤差を計算する。
2. 同じ `equipmentId` は加点するが、異なる機材名でも寸法と形状が近ければ候補に残す。
3. 矩形は0/90度の向きを比較し、寸法誤差が小さい向きを採用候補にする。
4. 円・多角形・複合形状は `shapeClass` と `areaRatio` を比較し、外形寸法だけが同じ異種形状の誤適用を避ける。
5. 全機材と全スロットを1対1で割り当て、割り当て総誤差が最小の組み合わせを求める。
6. 合計床面積差、個体寸法差、同一機材の一致数、対象荷台での余り幅・余り奥行きを総合スコアにする。
7. 許容誤差を超える機材が1点でもあれば、そのパターンは不採用にする。

初版の寸法許容差は、幅・奥行きそれぞれ5%を目安に実データで調整する。単純な配列順や機材名順ではなく、
最小費用の1対1割り当てとして実装することで、同寸法の重複機材や並び順の違いを扱えるようにする。

### 9.6 トラック幅への適応

機材や座標を比率で拡大縮小してはならない。初版では、パターンの実寸使用幅・使用奥行きが対象荷台へそのまま収まる場合だけ
候補にする。登録元より広いトラックでは左前を基準に同じ相対配置を使い、余った幅は空きとして残す。

登録元より狭い荷台へ適応する「行の組み直し」は次フェーズとする。その場合も座標を縮めず、保存済み座標から
行・列・同一機材ブロック・隣接関係を復元し、実寸のまま別の行へ送って再配置する。組み直した結果は必ず通常の
干渉判定と使用奥行き評価を通す。

### 9.7 候補の適用と既存アルゴリズムとの比較

パターン候補から配置を作るときは、対象機材の `id`、`equipmentId`、`snapshot` を保持し、座標と採用した回転だけを
候補スロットから設定する。適用後に次を確認する。

- 全点が対象荷台内に収まる。
- 障害物・他機材との重なりがない。
- 現在のクリアランスを満たす。
- 高さ・重量の既存警告を悪化させても隠さない。
- `stack_suggestion` は床面計算の評価から除外するが、画面上から削除しない。

正常なパターン候補、現在のブロック配置、既存の正常配置を同じ使用奥行き基準で比較する。初版UIでは類似度が高い候補を
最大3件表示し、Admin / Editorがプレビューして適用できるようにする。十分な実績が集まってから、最高スコア候補の
自動採用へ進める。候補適用は履歴上の1操作とし、1回のUndoで適用前へ戻せるようにする。

### 9.9 段階的な実装順

### 9.10 テストと完了条件

ユニットテスト:

- 同じ構成から同じ署名とfingerprintが得られる。
- 配列順が違っても同じ類似度・割り当てになる。
- 機材名が違っても寸法が許容範囲なら一致する。
- 同じ機材なら寸法が近い別機材より優先される。
- 0/90度の向きを比較できる。
- 矩形とL字など、外形だけ同じ異種形状を誤って一致させない。
- パターン使用幅・奥行きが荷台を超える場合は候補にしない。
- 適用後に要確認が1点でもあれば候補全体を棄却する。
- パターンが無い場合は既存自動配置と同じ結果になる。
- B型の `stack_suggestion` を1台だけ再現できる。

ブラウザ・RLSテスト:

- Adminだけに登録・管理UIが表示される。
- Adminは登録・編集・無効化・削除できる。
- Editor / Viewerは有効パターンを検索できるが、直接INSERT / UPDATE / DELETEするとRLSで拒否される。
- 11tトラックの20点構成で、類似候補の検索・プレビュー・適用・Undo / Redoが成立する。
- A型は使用奥行き3185mm・要確認0件を維持する。
- B型は20点・要確認0件のまま、UPA-AR 1台を縦積み候補として表示する。
- ESモジュールのキャッシュを無効化し、`npm run serve` のポート8090で確認する。

実装方針を確定して着手するときは、この節の内容を `project-docs/SPECIFICATION.md` のDB設計・権限・自動配置仕様へ反映する。
